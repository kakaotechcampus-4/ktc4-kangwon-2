# ADR-078: 교체 뒤 실패하면 서버 안의 deploy.sh 가 직전 성공 커밋으로 되돌린다

- 날짜: 2026-11-09
- 상태: 제안 — 구현됨(PR #452), 운영 연습 전. 연습(`docs/evaluation/09-deployment.md` 「더 모을 근거」)을 마치면 채택으로 바꾼다
- 번호: 처음에 075 로 잡았는데 #459(LLM 재시도)가 075 로 먼저 머지됐고, 076 은 #462, 077 은 하민 님 작업이 써서 078 로 옮겼다. #452 의 앞 커밋 메시지에 남은 「ADR-075」 · 「077」은 이 ADR 이다
- 구조가 한 번 바뀌었다: 처음(v1)은 서버 안에서 판정만 하고 되돌리기는 워크플로가 했다. 하민 님 리뷰(2026-11-09)를 받아 되돌리기를 서버 안으로 옮겼다 — 아래 「대안」

## 맥락

[실측] 배포 뒤 확인(`.github/workflows/deploy.yml` 「Health check」, `/health/ready` 30번)이 실패하면 run 이 실패하고
Discord 알림만 간다. 직전 버전으로 돌아가지 않는다 — 사람이 알림을 보고 손 롤백(`ref` 에 SHA)을 해야 한다.

[실측] 그 확인은 GitHub 러너가 인터넷을 건너 도메인으로 묻는다. 2026-10-11 배포는 서버가 멀쩡했는데 secret 에 남은 옛 IP 때문에
확인만 실패했다(`docs/evaluation/09-deployment.md` 「배포 사고 하나를 끝까지 추적했다」). 밖에서 본 실패로 되감으면
멀쩡한 새 버전을 옛 코드로 내린다 — 옛 코드는 새 코드가 쓴 JSONB 키를 저장할 때 버린다(같은 문서 「운영에서 롤백을 한 번 해 봤다」).

[실측] `scripts/deploy.sh` 는 `docker compose up -d` 와 nginx reload 뒤에 서비스가 떴는지 보지 않고 「배포 끝」을 찍는다.
실패한 명령의 종료 코드는 `set -e` 로 죽은 명령의 것이 그대로 나와, 코드 숫자만으로는 「교체까지 했는데 안 살아났다」를 다른 실패와 가를 수 없었다.

[실측] v1(워크플로가 되돌리기)에 대한 하민 님 리뷰에서 맞는 지적이 여럿 나왔다. ② 「마지막 성공」을 `gh run list` 의 생성 시각 순으로 고르면
옛 run 을 re-run 해서 되돌린 배포나 Session Manager 로 서버에서 직접 한 배포를 모른다. ④ 잠금 1500초에 작업이 붙으면 SSM 한도 1800초를 넘는다.
⑤ 배포와 되돌리기를 각각 최대 약 1900초씩 기다리면 OIDC 세션(기본 1시간)이 끝난다. ⑥ run 로그의 글자(`올릴 커밋 <SHA>`)로 대상을 찾으면
보관 기간이 지나거나 문구가 바뀔 때 대상이 비어 버린다. ⑨ 저장소 안의 `deploy.sh` 를 직접 돌리면 `git checkout -f` 가 bash 가 읽고 있는 파일을 바꾼다.

## 결정

**교체가 시작된 뒤에 실패하면, 서버 안의 `deploy.sh` 가 같은 실행 안에서 직전 성공 커밋 자신의 `deploy.sh` 를 꺼내 돌려 그 커밋으로 되돌린다.** 워크플로는 종료 코드를 읽어 알림만 낸다.

1. **서버가 「마지막 성공 커밋」을 기억한다.** 서버 안 확인을 통과할 때마다 `deploy.sh` 가 그 커밋의 전체 SHA 를 `/home/ubuntu/.ssuksak-last-good` 에 적는다.
   저장소 밖이라 checkout 이 안 건드린다. 읽을 때 40자리 16진수가 아니면 없는 것으로 친다(비었거나 깨졌다). 쓸 때는 임시 파일에 쓰고 옮긴다.
   **이 스크립트(v2)를 지난 성공만 기록된다.** 현재 워크플로의 자동 배포 · 손 배포(Run workflow) · 이 PR 이후 run 의 re-run, 그리고 서버에 v2 가 checkout 된 상태에서
   Session Manager 로 돌린 `deploy.sh` 는 다 반영된다. v2 가 머지되기 전 run 을 re-run 하거나(옛 커밋의 워크플로와 옛 `deploy.sh` 가 나간다),
   서버에 옛 커밋이 checkout 된 상태에서 그 `deploy.sh` 를 손으로 돌리면 성공해도 기록되지 않는다.
2. **서버 안 확인.** `deploy_one` 의 끝에서 `wait_ready` 가 서버 자신의 nginx 에 `http://127.0.0.1/health/ready`(backend · DB)와 `http://127.0.0.1/`(frontend 화면)를 묻는다.
   둘 다 200 이고 curl 도 종료 0 이어야 통과다. 2초 간격 30번(빠른 실패는 약 60초).
3. **교체 뒤 실패의 범위.** `up -d` 를 부르기 직전에 `swapped=1` 이 된다. 그 뒤의 `up -d` 실패 · nginx reload 와 restart 둘 다 실패 · 서버 안 확인 실패는 모두 「되돌린다」 쪽으로 간다.
   (`swap_failed` 는 `cmd || swap_failed "이유"` 로 부른다.) 그 앞의 실패(판정 거절 · checkout · nginx -t · build · alembic)는 컨테이너를 안 바꿨으므로 되돌리지 않는다.
4. **종료 코드.** `0` 성공 · `3` 교체 뒤 실패했고 L 로 되돌렸다 · `4` 교체 뒤 실패했고 못 되돌렸다 · `1` 교체 전에 멈췄다.
   몇 번인지는 `swapped` 하나가 정한다 — 명시적 `exit` 는 모두 `die` 를, 예상 밖 실패는 ERR 트랩(`on_err`)을 지나 `exit $((swapped ? 4 : 1))` 이다.
   교체 뒤의 어떤 실패도 1 로 새지 않고, 어떤 명령이 3 이나 4 로 죽어도 그 숫자는 안 나온다.
5. **되돌리는 조건과 방법**(하민 리뷰 ③). `AUTO_ROLLBACK=1` 이고 L(마지막 성공 기록)이 있고 L 이 이번에 올린 F 와 다를 때만 되돌린다.
   push 배포는 늘 `1`, 손 배포는 `auto_rollback` 입력대로 `deploy.yml` 이 넘긴다(`'1'` · `'0'` 문자열). Session Manager 로 손수 돌리면 없어서 꺼진다.
   되돌리기는 **L 의 `deploy.sh` 로** 한다:
   1. `git show L:scripts/deploy.sh` 를 임시 파일로 꺼낸다. 못 꺼내면(L 에 그 파일이 없다 · 커밋을 못 찾는다) 되돌리지 않고 4 다.
   2. **L 의 스크립트가 잠금을 직접 잡을 때만 서버 잠금을 푼다**(`exec 9>&-`). 표지는 꺼낸 파일 안의 `flock` 글자 하나다(`grep -q flock`).
      그런 자식은 같은 잠금을 기다리니, 안 풀면 부모를 `LOCK_WAIT` 만큼 기다리다 실패한다. 이 PR 보다 옛 스크립트(예: `4b786739`)에는 잠금이 없다 —
      풀면 되돌리기 내내 잠금 없이 도는 셈이라 Session Manager 배포가 끼어들 수 있다. 그 자식은 잠금을 달라고 하지 않으니 **쥔 채로 돌린다**(교착 없음).
      표지가 주석에만 있어도 풀지만 그건 아래 틈이 열릴 뿐 해롭지 않다. 반대(잠금을 잡는데 그 글자가 없음)는 `flock` 을 쓰지 않는 한 있을 수 없다.
   3. `env DEPLOY_REF=L AUTO_ROLLBACK=0 bash <임시 파일> 2>&1` 을 자식으로 돌린다. `AUTO_ROLLBACK=0` 은 자식이 또 되돌리지 않게 한다.
      자식의 stderr 는 **stdout 으로 합친다** — 옛 스크립트의 build 출력이 SSM stderr 한도(8000자)를 채워 부모의 결과 줄을 밀어내지 못하게 한다. 부모의 결과 줄만 stderr 에 남는다.
   4. 자식의 종료 코드를 `|| status=$?` 로 직접 받는다. 0 이면 `되돌렸다 → L (L 의 deploy.sh)` 와 3, 0 이 아니면(자식의 3 도) `되돌리기도 실패 — L 의 deploy.sh 가 <코드> 로 끝났다` 와 4 다.
      자식의 3 도 4 인 것은, 자식이 자기 직전으로 되돌렸어도 L 에 도착한 것이 아니기 때문이다.
   L 이 v2 이상이면 자식이 L 시절의 판정(ADR-073) · build · 교체 · 서버 안 확인을 L 의 코드로 하고 성공하면 L 을 다시 기록한다(같은 값). 부모의 `deploy_one L` 재귀는 없다.
6. **결과 줄은 stderr 로, 줄 맨 앞에.** `되돌렸다 → <L> (L 의 deploy.sh)` · `되돌리지 않는다 — <이유>` · `되돌리기도 실패 — <이유>`. SSM 이 stdout 은 앞 24000자만 돌려줘서 끝에 찍는 줄이 잘리기 때문이다.
   자식의 출력이 줄바꿈 없이 끝나도 결과 줄이 줄 맨 앞에 오게 빈 줄을 하나 찍고, `deploy.yml` 은 이런 줄 중 마지막 하나를 읽는다(자식이 자기 줄을 찍었어도 부모의 줄이 마지막이다).
   `직전 성공 <L 또는 없음>` 은 맨 앞 stdout 에 찍는다. `docker compose build` 출력은 서버 파일(`/tmp/ssuksak-build.log`)로 돌리고 실패했을 때만 끝 40줄을 보인다.
7. **시간.** 잠금 300초 + 이번 배포 + 되돌리기(L 의 스크립트가 자기 잠금을 다시 잡는다)가 SSM `executionTimeout` 2700초 안에 든다. 러너는 280번 × 10초(2800초)까지 기다린다 — 서버 명령이 한 번이라 OIDC 1시간 안이다.
8. **서버 잠금.** ubuntu 로 도는 쪽에서 `flock` 으로 `/tmp/ssuksak-deploy.lock` 을 잡는다. 워크플로 `concurrency` 는 러너 쪽만 막아서 손 배포와 자동 배포가 서버에서 겹치는 것을 이 잠금이 막는다.
   되돌리기 직전에는, L 의 스크립트가 잠금을 직접 잡는 경우에만 이 잠금을 푼다(위 5-2).
9. **스크립트 맨 끝은 `main "$@"; exit`.** 배포 도중 `git checkout -f` 가 이 파일을 바꿔도 bash 가 뒷부분을 더 읽지 않는다(하민 리뷰 ⑨).
10. **워크플로는 알림만.** `gh run list` · 로그 읽기 · `actions: read` 가 없다. 「배포」 스텝이 종료 코드와 결과 줄을 output 으로 남기고, 「Health check」(밖에서 확인)는 코드가 0 이나 3 일 때만 돌며 실패해도 되돌리지 않는다.
   코드가 0 이 아니면(3 포함) run 은 실패로 끝난다 — 되돌렸어도 이번에 올리려던 배포는 실패다. 알림은 3 🟠(push 면 「브랜치 끝은 아직 그대로다 — 되돌리는 PR 이 필요하다」) ·
   3 인데 밖에서 안 닿음 · 4 🔴(서버가 알린 이유) · 1 · 124 · 125 · 0 인데 밖에서만 안 닿음.

## 근거

- [실측] 2026-11-09 운영 서버에서 읽기 전용(SSM)으로 확인했다. 서버 안에서 `curl http://127.0.0.1/health/ready` 와 `http://127.0.0.1/` 가 둘 다 200, 약 0.004초다.
  nginx 로그의 출발지는 `172.28.0.1` 이다 — `nginx/nginx.conf` 의 localhost 블록이 받는다(`allow 172.28.0.1`). `localhost` 는 `::1` 로 붙어서 구현은 `127.0.0.1` 로 IPv4 를 고정한다.
- [실측] 10-11 의 옛 IP 사례(맥락)가 밖에서 본 실패로 판정하면 안 되는 이유다. 서버 안 판정은 DNS · 인증서 · IP 가 끼지 않는다.
- [실측] **SSM stdout 은 앞 24000자만 온다.** run `42505477177` 의 서버 출력이 `next build` 출력 한가운데에서 `--output truncated--` 로 끝났다. 그래서 끝에 찍는 결과 줄은 stdout 으로 못 보낸다 —
  stderr 는 한도가 따로(8000자)이고 평소 2K 안팎이다. build 출력을 파일로 돌리면 stdout 도 줄어 `wait_ready` 진단 줄이 보인다.
- [실측] 하민 리뷰 ① 의 전제는 달랐다. `docker-compose.yml` 에서 frontend 는 backend 의 healthy 를 기다리지 않고(`depends_on: service_healthy` 는 backend → db 만 있다) backend 에는 healthcheck 가 없어서,
  새 backend 가 죽어도 `up -d` 는 성공하고 서버 안 확인이 잡는다. 그래도 「교체가 시작된 뒤의 실패(`up -d` · nginx reload/restart)도 되돌린다」는 받아서 `swapped` 로 정했다.
- [실측] ERR 트랩은 `set +e` 로 감싼 구간에서도 외부 명령 실패에 걸려 종료 코드를 1 로 만든다. 맥의 bash 3.2 에서 시험했고, 서버(bash 5)에서는 CI 와 운영 연습이 확인한다.
  그래서 root → ubuntu 래퍼를 `|| status=$?` 꼴로 바꿨고, 가짜 `runuser` 로 root 에서 시작해 3 · 4 가 그대로 나오는지 테스트가 본다(`backend/tests/test_deploy_script.py`).
  `$(…)` 안에서 죽은 명령의 코드도 1 로 바뀐다 — curl 종료 코드 28 이 1 로 찍혔고(`probe`), `revision_file` 은 git grep 이 깨진 코드(128)가 1(못 찾음)로 뭉개져
  「마이그레이션 폴더를 읽지 못했다」 거절이 develop 쪽 이유로 샜다. 둘 다 테스트가 잡았고 안쪽에서 `||` 로 코드를 받게 고쳤다.
- [실측] `||` · `&&` · `if` 의 왼쪽에서 부른 함수 안에서는 errexit 도 ERR 트랩도 꺼진다. `deploy_one` 을 거기서 부르면 실패한 단계를 넘어 계속 가고 「되돌렸다」고 거짓말한다.
  그래서 `deploy_one` 은 늘 맨몸으로 부르고, 교체 뒤 단계만 `|| swap_failed` 로 받는다(`swap_failed` 는 그 오른쪽이라 꺼지지 않는다). 자식의 종료 코드도 같은 이유로 `|| status=$?` 로 직접 받는다
  (`|| true` 로 바꾸면 자식이 실패해도 3 이 되어 「자식 코드 ≠ 0 이면 4」 테스트가 실패한다 — 줄 지우기 시험).
- [판단] 하민 리뷰 ③ — F 의 `deploy.sh` 로 되돌리면 F 가 그 스크립트(`wait_ready` 포함)를 망가뜨렸을 때 되돌리기도 같이 실패한다. 실패한 커밋의 코드에 복구를 맡기지 않는다.
  L 은 한 번 서버 안에서 성공한 커밋이고 그 시절의 스크립트가 그 시절의 판정 · build 를 안다.
- [실측] 테스트가 네 코드를 모두 본다. 가짜 저장소의 L 커밋(a1)에 시험용 `scripts/deploy.sh` 가 들어 있고(부른 모습과 env 를 기록하고, 서버 잠금이 풀려 있는지 `flock -n` 으로 잡아 보고,
  가짜 서버를 L 로 돌려 놓고, `FAKE_L_EXIT` 로 끝난다), F 커밋(c)에는 일부러 망가뜨린 스크립트가 들어 있다. 가짜 `curl` 은 도는 컨테이너가 나쁜 커밋 목록에 있으면 503 을 답한다.
  F 가 안 살아남 → 롤백이 켜져 있으면 L 의 스크립트가 `DEPLOY_REF=L` · `AUTO_ROLLBACK=0` 으로 돌고(F 의 것은 안 돈다) 시작할 때 잠금이 풀려 있고 3,
  자식이 0 이 아니면(1 · 3 · 4 · 255) 4, 꺼져 있거나 · 기록이 없거나 · 깨졌거나 · L 이 F 와 같거나 · L 에 `deploy.sh` 가 없으면 4(L 의 스크립트는 안 돈다),
  `up -d` 실패 · reload 와 restart 둘 다 실패도 되돌린다, 교체 전 실패(가짜 build 가 3 으로 죽음)는 1, root 로 시작해도 3 · 4 가 같다.
  마이그레이션 판정(ADR-073)은 되돌리기 안으로 들어가 L 의 스크립트가 하므로, 판정 자체는 `migration_step` 테스트가 계속 본다.
  `ssm-deploy.sh` 는 가짜 `aws` 로 상태별 종료 코드와 보내는 `commands`(쉬뱅 첫 줄 · `AUTO_ROLLBACK`)를 본다(`backend/tests/test_ssm_deploy_script.py`).
- [판단] 4 는 「서비스가 어떤 상태인지 모른다」다. 컨테이너를 바꿨는데 되돌리지 않았거나 못 되돌렸으므로 사람이 서버를 봐야 한다. 1 은 컨테이너를 안 바꿨다(checkout · build · alembic 은 했을 수 있다).
  124 · 125 는 러너 쪽에서 서버가 어떤 상태인지 모른다.
- [판단] `AUTO_ROLLBACK` 을 환경변수로 받는다. 이 파일의 상수(`LOCK_WAIT` 등)는 「서버에 남은 값이 배포를 바꾸면 안 된다」며 환경변수로 안 받지만, 이 값은 호출하는 쪽이 정하는 입력이고
  켜는 쪽으로만 작용한다. 서버에 남아 있어도 되돌리기를 켤 뿐이라 안전한 쪽으로 틀린다.
- [판단] 2초 × 30번(약 60초)은 11-07 롤백 연습에서 `up -d` 가 backend · frontend 를 바꾸는 동안의 끊김이 약 5초였던 것에 비해 12배 여유다.
- [판단] 설계안(v1)은 opus 검토와 Codex 플랜 검사를 거쳤고, v2(서버 안 롤백)는 하민 리뷰를 받아 opus 플랜 검사 11건을 반영했다.

## 대안

- **알림만 둔다(최소안)** — 지금 그대로다. 사람이 알림을 보고 직전 SHA 를 찾아 손 롤백한다. 사람이 없는 시간에는 장애가 길어진다.
- **밖에서 확인(Health check)이 실패하면 되돌린다** — 10-11 의 옛 IP 처럼 서버가 멀쩡한데 새 버전을 내린다. DNS · 인증서 · secret 이 원인이면 되감아도 안 고쳐진다.
- **v1: 워크플로가 되돌린다** — `deploy.sh` 가 서버 안 확인에서 3 으로 끝나면 `deploy.yml` 이 `gh run list --status success --limit 1` 의 run 로그에서 `올릴 커밋 <SHA>` 줄을 읽어
  SSM 을 한 번 더 보냈다. 하민 리뷰 ② ④ ⑤ ⑥ 이 모두 맞아 버렸다(맥락) — 「마지막 성공」을 Actions 기록으로 알려면 서버에서 일어난 배포(re-run · Session Manager)가 빠지고,
  로그 글자에 기대고, 서버 명령이 두 번이라 대기도 두 번이다. 되돌리기 로직이 워크플로 셸에 있어 단위 테스트도 못 했다. 서버가 직접 기억하면 넷이 한꺼번에 없어진다.
- **서버의 `git rev-parse HEAD` 를 L 로 쓴다**(하민 제안) — 교체 전에 서버 HEAD 를 읽어 두면 기록이 따로 필요 없다. 안 쓴 이유: `deploy_one` 에서 checkout 이 build · alembic 보다 앞이라,
  교체 전에 실패한 배포(build 실패 등) 뒤에는 서버 HEAD 가 F 로 옮겨 가 있는데 컨테이너는 아직 옛 커밋으로 돈다. 다음 배포가 실패하면 HEAD 를 L 로 읽어
  「F 폴더 + 옛 컨테이너」 쪽으로 되돌아간다. 서버 안 확인을 통과한 커밋만 적는 기록 파일은 이 어긋남이 없다.
- **F 의 스크립트로 되돌린다**(이 PR 의 앞 구현: 부모 안에서 `deploy_one L` 을 한 번 더 불렀다) — 한 프로세스 안이라 잠금 틈이 없고 단순하다. 하지만 F 가 `deploy.sh` 를 망가뜨렸으면 되돌리기도 실패한다
  (하민 리뷰 ③). 되돌릴 일이 생기는 바로 그 경우다.
- **자식에게 「잠금은 이미 내가 잡았다」를 env 로 알린다** — 틈은 없어지지만 L 이 옛 스크립트면 그 env 를 모른다. 옛 스크립트가 같은 잠금을 기다리다 교착되거나(잠금이 있던 스크립트일 때),
  잠금이 아예 없다. 풀고 L 이 다시 잡게 하는 편이 L 이 어떤 시절 스크립트여도 맞는다.
- **롤백을 새 `workflow_dispatch` 로 자기 호출한다** — `actions: write` 권한이 필요하고, 같은 `concurrency` 그룹이라 새 run 은 현재 run 이 끝나야 시작한다. 서버가 죽은 채 기다린다.
- **DB 를 자동으로 내린다** — ADR-073 과 같은 이유로 안 한다. 데이터가 지워질 수 있다.

## 결과

- `deploy.sh` 는 `deploy_one`(판정 → checkout → nginx -t → build → 마이그레이션 → up -d → reload → 서버 안 확인)을 부르고, 통과하면 기록 · prune · 「배포 끝」을 한다.
  교체 뒤 실패하면 `swap_failed` 가 L 의 `deploy.sh` 를 꺼내 자식으로 돌린다.
  `deploy.yml` 의 「자동 롤백」 스텝 · `actions: read` · `gh run list` 는 없어진다. 서버 명령은 한 번이고 러너는 한 번만 기다린다.
- 종료 코드에 뜻이 생겼다(0 · 3 · 4 · 1). 서버에는 잠금과 `/home/ubuntu/.ssuksak-last-good` 가 생긴다. 서버에서 쓰는 곳이 하나 더 늘었다.
- 자동 롤백이 돌면 서버는 L 로 돌지만 run 은 실패로 남는다. 브랜치 끝은 그대로라 **되돌리는 PR 이 필요하다** — 안 하면 다음 머지가 같은 실패를 되풀이할 수 있다.
- 손 배포 입력 `auto_rollback`(기본 꺼짐)은 남는다. 설명만 「서버가 기억한 마지막 성공 배포로」로 바뀐다.
- 이 ADR 의 PR 은 GitHub 설정을 바꾸지 않는다.

## 한계

- **응답 코드만 본다.** 화면이 뜨지만 내용이 깨진 경우, 기능 버그(ready 200 이면 안 걸린다)는 못 잡는다. 인증서 · DNS · IP 문제는 알림만 간다.
- **`/health/ready` 에 DB 가 들어 있다**(하민 리뷰 ⑦). 배포 중 Postgres 가 60초 넘게 끊기면 멀쩡한 코드가 되돌려진다. 다만 DB 가 끊긴 채면 되돌리기도 DB 리비전 읽기에서 멈춰 서버를 안 바꾼다(4).
  DB 확인을 빼면 「새 코드가 DB 에 못 붙는」 장애를 놓친다 — 그대로 둔다.
- **L 의 스크립트가 잠금을 직접 잡을 때만(= 이 PR 이후 스크립트일 때만) 잠금을 푸는 순간부터 자식이 다시 잡을 때까지 틈이 있다.** 그 사이 다른 배포가 잠금을 잡을 수 있다.
  Actions 배포끼리는 `concurrency` 가 막아서 Session Manager 로 손수 돌린 배포와 겹칠 때만 열린다. 틈은 자식이 `flock` 에 닿기까지의 짧은 시간이라 두고 간다
  (자식에게 잠금을 넘기는 대안은 L 이 옛 스크립트일 때 안 통한다). 잠금을 모르는 옛 L 은 부모가 잠금을 쥔 채 돌려서 틈이 없다.
- **옛 L 스크립트의 출력은 stdout 한도(24000자)를 쓴다.** 자식의 stderr 를 stdout 으로 합치므로 build 출력이 길면 stdout 뒤쪽이 잘린다. 결과 줄은 stderr 에 있어서 안 잘린다.
- **L 이 이 PR 보다 옛 스크립트면 서버 안 확인이 없다.** 그 스크립트의 0 은 「배포는 끝남」까지만 뜻하고 살아났는지는 모른다. 그때는 `deploy.yml` 의 밖 확인(종료 코드 3 일 때 돈다)이
  「되돌렸는데 밖에서 안 닿음」으로 대신 알린다. L 이 #445 보다 옛 스크립트면 마이그레이션 판정도 없어서 DB 가 앞서 있으면 alembic 이 멈춰 4 다.
  L 이 이 PR 보다 옛 것이면 L 의 스크립트는 `AUTO_ROLLBACK` 도 `LAST_GOOD_FILE` 도 모른다 — 기록은 안 바뀐다(L 이 이미 적혀 있다).
- **시작이 기다림보다 느리면 멀쩡한 판도 되돌려진다.** 2초 × 30번(빠른 502 · 503 이 오면 약 60초) 안에 둘 다 200 이 안 되면 실패다 —
  예컨대 frontend 가 61초 뒤에 200 이 되는 판. 손잡이는 `deploy.sh` 의 `READY_TRIES` · `READY_INTERVAL` 이다. 지금은 30 × 2초로 둔다.
- **`/` 가 인증 없이 200 을 준다는 가정이다**(2026-11-09 운영에서 200 확인). 화면이 로그인 쪽으로 3xx 를 내게 바뀌면 모든 배포가 실패로 판정돼 자동 롤백이 돈다. 그때는 확인 주소(`wait_ready` 의 `/`)를 고친다.
- **기록은 v2 `deploy.sh` 를 지난 성공만 반영한다.** 옛(v1 이전) run 을 re-run 하거나 옛 체크아웃의 `deploy.sh` 를 손으로 돌려 옛 버전 Y 를 올리면 그 성공은 기록되지 않아,
  그 뒤 실패했을 때 실제로 돌던 Y 가 아니라 기록에 남은 더 앞의 X 로 되돌아간다. 옛 버전을 서버에 올릴 때는 현재 워크플로의 Run workflow 에 `ref=<과거 SHA>` 를 넣는다
  (옛 run 의 re-run 도, 옛 스크립트를 손으로 돌리는 것도 아니다) — 그러면 현재 `deploy.sh` 가 돌아 Y 가 기록된다.
- **이 PR 이 머지된 뒤 첫 성공 배포 전에는 기록 파일이 없다.** 그 사이 실패하면 「직전 성공 기록이 없다」로 4 다. 서버의 기록 파일이 지워져도 다음 성공 배포까지 롤백이 없다.
  기록 파일을 손으로 심지는 않는다 — 머지 배포가 성공하면 생긴다.
- **마이그레이션 판정(ADR-073)이 거절하면 사람이 한다**(L 의 스크립트가 1 로 끝나 4). ADR-073 이 건너뛰게 하는 것은 develop 이력에서 DB 리비전을 들여온 PR 의 머지 직전 커밋 하나뿐이다.
  `concurrency` 가 대기 중인 run 을 취소해서 L 이 B 보다 옛 커밋이 되면 거절된다. `backend (rollback compat)` 가 아직 필수 검사가 아니라서(ADR-073 「한계」) 자동 건너뛰기가 시험 안 된 조합으로 갈 수도 있다.
- **롤백 뒤에도 브랜치 끝은 그대로다.** 되돌리는 PR 없이 다음 머지가 들어오면 같은 실패가 다시 난다.
- **손 배포가 잠금을 300초 넘게 쥐면 push 배포는 1 로 멈춘다**(서버는 안 바뀐다). 잠금 + 배포 + 되돌리기가 SSM 한도 안에 들어야 해서 줄였다.
- **실패한 컨테이너 로그가 되감기(컨테이너 재생성)로 사라진다.** journald 로 남기는 설정(ADR-058)이 켜져 있어야 남는다.
- **`production` environment 에 보호 규칙(승인자)을 켜면 이 설계를 다시 본다.** 되돌리기가 승인 없이 서버를 바꾼다.
- **알림 갈래는 단위 테스트가 없다.** 워크플로 안의 셸이라서다. 가짜 `ssm-deploy.sh` · `curl` 로 갈래마다 한 번씩 손으로 돌려 봤고(저장소에 넣지 않았다) 나머지는 운영 연습이 본다.
- **운영 연습 전이다.** 머지 배포가 성공해 기록이 생긴 뒤, 그 위에서 `/health/ready` 만 503 을 내는 커밋 F 를 `auto_rollback=true` 로 손 배포해
  3 → 서버 HEAD = L → 서버 안 · 밖 ready 200 → 알림까지 본다.
- **flock 은 서버에 `flock`(util-linux)이 있어야 한다.** 우분투 기본이다. 없으면 배포가 멈춘다.
