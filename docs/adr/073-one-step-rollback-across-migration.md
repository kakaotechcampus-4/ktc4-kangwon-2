# ADR-073: 마이그레이션 PR 하나까지는 되감는다 — CI 가 시험한 코드로만, 그 밖은 서버를 건드리기 전에 멈춘다

- 날짜: 2026-11-08
- 상태: 채택. CI 필수 검사를 켜기 전에는 `backend (rollback compat)` 가 경고등이다 — 켜는 일은 이 ADR 이 하지 않는다 · 보충 — ADR-094(배포를 main 머지로 옮긴 뒤 main 이력에서도 찾는다)

## 맥락

[실측] `scripts/deploy.sh` 는 `alembic upgrade head` 만 돈다. DB 가 옛 코드가 모르는 리비전에 서 있으면
`Can't locate revision` 으로 거기서 죽는다(`docs/deploy.md` 「되감을 때 (롤백)」, 멘토 지적 #210).
죽는 시점에 서버 폴더와 빌드된 이미지는 이미 옛 코드다. 마이그레이션이 든 PR 을 건너는 롤백을 deploy.sh 가 처리하지 못한다.

[실측] 2026-10-20 부터 `docs/deploy.md` 에 「열을 지우거나 이름을 바꾸는 변경은 두 단계로 나눠 올린다
(먼저 안 쓰게 하고, 다음 판에서 지운다)」는 규칙이 있다. #383 은 계획안 확정에 CHECK 제약을 걸었고, #415 는
`center_invites` 표를 지웠다 — 둘 다 그 전 코드가 쓰는 것인데 두 단계로 나누지 않았다. 문서 규칙은 지켜지지 않았다.
어기면 막는 장치가 없었다(`docs/evaluation/09-deployment.md`).

[실측] #424(`89e84790`)가 `e3b9f4a1c7d2`(`users_kakao_id`)를 더했다. 그 DB 에서 #424 직전 `de04e2c0` 로 되감으면
코드는 새 스키마에서 돌아도(아래 근거) deploy.sh 가 upgrade 에서 멈춘다.

## 결정

롤백이 마이그레이션을 건너도 되는 경우를 **CI 가 시험한 조합 하나**로 좁히고, 그 밖은 서버를 바꾸기 전에 멈춘다.

1. **CI `backend (rollback compat)`.** develop 으로 가는 PR 중 마이그레이션이 바뀐 것에서만 돈다(`ci.yml`). 코드는 PR 머지 커밋 M 의 첫 부모 B 이고,
   `backend/alembic/versions` 만 M 의 것이다. backend pytest 가 전부 통과하면 초록이다 — 대조군과 비교하지 않는다.
   **이미 있는 리비전 파일을 고치거나 지운 PR 은 이 job 이 실패한다**(운영 DB 에 올라간 리비전이 바뀌기 때문).
2. **`deploy.sh` 가 checkout 전에 판정한다.** 지금 도는 backend 이미지로, 앱이 쓰는 `DATABASE_URL` 그대로 `alembic_version` 을 읽는다(R).
   `migration_step` 이 글자 하나로 답한다.

   | 상황 | 답 |
   |---|---|
   | R 이 하나가 아니거나 12자리 16진수가 아니다 | `reject` |
   | 올릴 커밋이 R 을 선언한 파일을 가진다 — 평소 배포 · 같은 SHA 재배포 · 다시 앞으로 · 마이그레이션 없는 PR 만 건너는 되감기 | `upgrade` |
   | 올릴 커밋은 R 을 모르고, develop 의 first-parent 에서 R 을 처음 들여온 커밋 M 의 첫 부모 B 가 올릴 커밋이다 | `skip` — `alembic upgrade` 를 건너뛴다 |
   | 그 밖 — B 가 아니다(둘 이상 건너뜀 · 다른 갈래) · develop 도 R 을 모른다 | `reject` — checkout · build 전에 `exit 1` |

3. **develop 규칙을 켤 때 필수 검사 목록에 `backend (rollback compat)` 를 더한다.** 「브랜치를 최신으로」(strict)는 이미 켜져 있다.
   이 ADR 의 PR 은 GitHub 설정을 바꾸지 않는다.

## 근거

- [실측] 2026-11-08 로컬 시험 — 각 PR 의 머지 직전 코드를 그 PR 의 마이그레이션까지 올린 DB 에서 pytest 로 돌렸다.
  #383 은 기준선에 없던 실패 135개가 나왔고 전부 연간 확정 500(`ck_plans_confirmed_has_class_snapshot` 제약)이었다.
  #371 · #424 는 새 실패 0 이었다. 같은 일이 PR 마다 CI 에서 돈다면 #383 은 머지 전에 빨개졌을 것이다.
- [실측] 2026-11-08 실제 이력에서 `migration_step` 을 불러 봤다(DB 가 `e3b9f4a1c7d2` 라고 치고).
  #424 직전 `de04e2c0` → `skip e3b9f4a1c7d2 89e84790… de04e2c0…`, 그때 develop 끝 `42f6137e` → `upgrade`,
  #383 직전 `458a2bf7` → `reject … de04e2c0 로만 된다`. 가짜 `sudo` 와 로컬 bare 저장소로 `main` 도 돌려 봤다 —
  건너뜀 경로는 `alembic upgrade` 없이 끝나고, 거절은 checkout 전에 멈춰 서버 HEAD 가 그대로다.
  서버 · 진짜 docker 는 쓰지 않았다. 판정표는 `backend/tests/test_deploy_script.py` 가 임시 저장소에서 CI 마다 본다
  (CI 는 이력을 얕게 받아서 위 실제 커밋을 직접 시험에 쓰지 못한다).
- [판단] **서버가 도는 커밋이나 리비전의 부모로 판정하면 안 된다.** 「A 는 어떤 칸을 쓰고, B 는 안 쓰고, C 가 그 칸을 지운다」를 보자.
  C 의 CI 는 C 직전 코드 B 만 새 스키마에서 시험한다. 리비전 부모로 보면 A 도 C 의 직전 리비전을 가졌으니 허용되는데,
  A 는 지워진 칸을 쓰므로 새 스키마에서 깨지고 아무도 시험한 적이 없다. **시험한 B 로만** 건너뛰면 이 반례가 닫힌다.
- [판단] base 를 `HEAD^1` 로 잡아도 B 와 같다. develop 규칙의 strict 가 PR 머지 커밋의 첫 부모를 머지 시점 develop 끝으로 고정하고,
  머지하면 그 커밋이 M 의 앞 커밋이다. 저장소 설정은 merge commit 만 허용한다 — `M^1` 이 B 라는 가정이 거기 기댄다.
- [실측] `revision = '…'` 와 `revision: str = "…"` 두 꼴이 섞여 있어, 파일 이름이 아니라 선언을 본다. 실제 리비전 전부를
  `revision_file` 이 선언한 파일로 찾는지 시험한다 — `backend/tests/test_deploy_script.py`.

## 대안

- **문서 규칙만 둔다** — 이미 있었고(2026-10-20) 두 번 어겨졌다. 사람이 기억해야 하는 규칙은 어긴 줄을 모른다.
- **리비전의 부모로 판정한다** — 위 반례(A · B · C).
- **CI 결과를 배포로 넘긴다** — 배포가 CI 에 기대게 된다. 지금은 CI 가 실패해도 배포되고(`ci.yml` 과 `deploy.yml` 이 따로 돈다),
  넘길 통로를 새로 만들어야 한다. 위 결정은 CI 가 시험한 조합을 **코드 모양(B)** 으로 다시 찾아 통로 없이 같은 결론에 닿는다.
- **DB 를 자동으로 내린다(downgrade)** — 데이터가 지워질 수 있다. 사람이 백업하고 `downgrade()` 를 읽은 뒤에만 한다(`docs/deploy.md`).

## 결과

- 마이그레이션이 든 PR 은 CI 에 job 이 하나 더 돈다. 옛 코드가 쓰는 열 · 표를 지우거나 제약을 거는 PR 은 머지 전에 빨개진다.
- 이미 있는 리비전 파일을 고치거나 지우는 PR 은 막힌다.
- 롤백은 **마이그레이션 PR 하나까지** 된다. 건너뛰면 deploy.sh 로그에 「마이그레이션을 건너뛴다 — … ADR-073」이 남고,
  못 가는 곳은 이유 한 줄과 함께 서버를 바꾸기 전에 멈춘다. 서버 폴더 · 이미지 · 컨테이너가 그대로라 다시 시도할 수 있다.
- `docs/deploy.md` 「되감을 때 (롤백)」과 `docs/evaluation/09-deployment.md` 「아직 아닌 것」을 이 결정에 맞췄다.

## 한계

- **한 칸이다.** 마이그레이션 PR 을 둘 이상 건너뛰는 롤백은 전처럼 DB 를 손으로 내려야 한다(`docs/deploy.md` ②).
- **테스트가 덮는 경로만 본다.** pytest 가 안 지나는 코드는 시험한 적이 없다.
- **빈 DB 에서만 시험한다.** 기존 데이터 · 새 코드가 쓴 데이터를 옛 코드가 읽는지는 안 본다. JSONB 안의 새 키처럼
  마이그레이션 없는 스키마 변경도 이 검사 밖이다.
- **소급되지 않는다.** #383 · #415 이전에 이미 든 변경은 시험한 적이 없다.
- **B 가 실제로 배포된 적 없을 수 있다.** 연속 머지로 앞 배포 run 이 취소되기도 한다. 그래도 CI 가 시험한 조합이다.
- **평소 배포의 몇 초 동안 도는 옛 앱이 B 가 아닐 수 있다.** `alembic upgrade` 가 끝나고 `up -d` 가 교체하기 전까지는 직전 배포의 코드가
  새 스키마에서 돈다. 연속 머지가 있었으면 그것이 B 가 아니다. 이 틈은 전에도 있었다.
- **배포 브랜치가 develop 인 동안의 설계다.** CI 의 B 와 deploy.sh 의 M 찾기가 둘 다 develop 의 first-parent 이력을 본다.
  `main` 으로 가는 PR 에는 이 job 이 돌지 않고, `main` 에서 `main^1` 로 마이그레이션을 건너는 롤백은 거절된다.
  배포를 다시 `main` 만으로 옮길 때(develop 머지 = 배포는 임시다) 이 ADR 을 다시 본다 — 그때 시험한 B 는 운영 코드가 아니다.
- **develop 을 올려 둔 서버에 `main` 배포를 돌리면 멈출 수 있다.** develop 에만 있는 마이그레이션이 DB 에 올라갔고 `main` 이 그것을 모르면
  `main` 끝이 그 PR 의 머지 직전 커밋이 아닌 한 거절된다. 이때도 서버는 바뀌지 않는다.
- **merge commit 전제.** 저장소가 merge 방식만 허용하는 동안만 `M^1` 이 B 다. squash · rebase 를 켜면 이 판정과 CI 가 같이 틀린다.
- **최초 구축(DB 없음)은 범위 밖이다.** `alembic_version` 이 없으면 deploy.sh 가 DB 리비전을 못 읽고 멈춘다. 그때는 DB 를 띄우고
  `alembic upgrade head` 를 손으로 한 번 돌려 표를 만든 뒤부터 쓴다 [판단].
- **필수 검사로 켜기 전에는 경고등이다.** compat job 이 빨개도 머지되면, deploy.sh 는 CI 결과를 모른 채 그 조합을 건너뛰기로 허용한다.
