# ADR-077: 관찰일지는 만들 때의 입력을 사본으로 갖는다 — 근거마다 날짜 · 영역 · 상황, 문서마다 영역 축

- 2026-11-09
- 상태 — 채택 (PM 승인 2026-11-09)
- 관련 — ADR-024(결정 4 · 결과) · ADR-073 · api-spec §10 · §11
- 번호 — develop 의 마지막은 074 다. 하민님 `chore/pseudonymize-institution` 의 074 는 develop 의 074 와 겹쳐 번호를 다시 받아야 하고,
  `feature/auto-rollback` 이 075 를 쓴다. 하민님이 다시 받을 076 을 비워 두고 077 을 쓴다.

## 맥락

관찰일지는 근거 관찰 기록의 **사실 · 날짜만** 사본(`document_sources`)으로 남겼다. 영역은 종이를 만들 때 원본에서,
영역 축(5영역 ↔ 일상생활 · 놀이활동)은 원 설정에서 그때그때 읽었다.

- [실측] 확정한 관찰일지의 근거 기록에서 영역만 바꾸면 `stale` 이 되지 않고, 종이의 영역 행이 새 영역으로 옮겨 갔다.
  배움 칸(해석)은 옛 영역의 누리과정 내용으로 쓴 글이다(draft v3). 교사가 확정한 것과 다른 종이가 나간다.
- [실측] 원이 영역 축을 바꾸면 그 전에 확정한 관찰일지 내보내기가 422 였다. 새 양식에 옛 영역 줄이 없다.
- [실측] 관찰 기록의 상황(`context`)은 사본에도, LLM 입력에도, 종이에도 쓰이지 않았다. 교사가 적은 입력이 버려졌다.
- [실측] LLM 은 사실 글만 받았다. 날짜를 못 받으니 「9월 5일에는 … 9일에는」처럼 시간 순서를 쓸 수 없었다.

ADR-024 결과의 「`observation` 의 `sources` 가 `domain` 을 같이 준다」는 원본에서 읽은 값이었다. api-spec §11 은
「영역만 고치면 `stale` 이 아니므로 고친 값이 나간다」고 적었다.

## 결정

1. **문서는 만들 때의 입력을 사본으로 갖는다.** 관찰 기록 근거마다 날짜 · 영역 · 상황(`document_sources.date` · `domain` · `context`),
   문서마다 영역 축(`documents.observation_axis`). 축은 그 원이 **문서를 만들 때** 쓰던 축이다.
2. **종이 · 미리보기 · `stale` 판단은 사본만 본다.** 관찰 칸 한 줄은 `(9/5) (바깥놀이) 사실` 이다 — 상황이 비었으면 괄호를 붙이지 않는다.
   hwpx 양식 파일은 그대로다. 채우는 글만 바뀐다.
3. **사실 · 날짜 · 영역 · 상황 중 하나라도 바뀌면 `stale` 이다.** api-spec §11 「영역만 고치면 `stale` 이 아니다」를 뒤집는다.
4. **축이 다른 원본으로 `refresh` 하는 것은 거절한다.** 409 `GATE_BLOCKED`, `fields` 에 그 근거. 문서는 `stale` 그대로다.
   만들 때도 원의 지금 축이 아닌 기록은 근거로 받지 않는다(422 `sources.{id}`) — 그 양식에 넣을 줄이 없다.
5. **LLM 은 사실마다 `{fact, date, domain, context}` 를 받는다.** 가명 치환은 `fact` · `context` 둘 다 한다.
   `generation.rule_version` 은 `v4` 다. 숫자 게이트(2단)는 상황의 숫자를 사실처럼 근거로 친다 — 교사가 준 입력이라
   지어낸 숫자가 아니다. 근거 날짜의 연 · 월 · 일은 **해석의 날짜 표현(「11월」 「4일」 「11/4」) 안의 숫자에만** 근거다.
   개수 · 횟수(「4개」)는 사실 · 상황의 숫자와만 견준다.
   **AI 검토(3단, ADR-071)도 같은 사본 칸을 근거로 받는다.** 생성이 상황을 보고 쓴 장소 · 함께한 사람을 검토가
   「기록에 없는 일」로 읽지 않게 한다. 검토의 이름 표는 사실 · 상황 · 해석 · 지원 글로 만든다.
6. **사본이 없는 옛 문서는 「다시 확인」이다.** 아래 채우기 규칙이 확실하게 채우지 못한 행은 NULL 로 두고, 그 문서는 예전처럼
   원본 영역 · 원의 지금 축을 읽는다. 상황은 쓰지 않는다. 원본 영역이 실제로 바뀌면 `stale` 이다(종이가 원본을 따르므로).
   `refresh` 하면 지금 원본으로 사본을 뜨고 원의 지금 축을 찍어 「다시 확인」이 풀린다.
   **「다시 확인」 문서의 확정 · 내보내기를 막을지는 아직 정하지 않았다(PM 결정).** 지금은 막지 않는다.

### 기존 행 채우기 규칙 (마이그레이션 `6aca7868e15a`)

```
근거 사본   원본 updated_at < 문서 created_at - 1분  이고
           사본 text · date 가 원본 fact · date 와 같다   →  원본의 영역 · 상황
문서 축     관찰 근거의 영역을 모두 알고, 모두 한 축에 든다   →  그 축
그 밖       NULL — 「다시 확인」
```

## 근거

- [실측] 재현 테스트 S1 · S7 · G1 · G2 — 위 맥락의 넷이 지금 코드에서 일어났다. 이 결정 뒤 `tests/test_documents_input_snapshot.py` 가
  뒤집힌 단언으로 본다.
- [판단] 영역은 종이의 행을 정하고 배움 칸의 근거(누리과정 내용)를 정한다. 사실과 같은 무게의 입력이다. 「사실이 그대로면 그대로」라는
  옛 판단은 영역이 종이에 쓰이지 않던 때의 것이다.
- [판단] 축은 양식을 정한다. 원이 축을 바꿨다고 이미 확정한 종이의 모양이 바뀌면 안 된다. 계획안이 확정 때 반 이름을 찍는 것(ADR-062)과 같은 이유다.
- [판단] 채우기의 1분 여유 — 생성은 사본을 만든 뒤 모델을 기다리고 저장한다. 그 사이 고친 원본은 `updated_at` 이 문서 `created_at` 과 몇 초 차이다.
  그 기록은 만들 때 값과 다를 수 있어 넣지 않는다. 문서보다 1분 넘게 먼저 마지막으로 고쳐졌으면 만들 때 원본도 지금 값이었다.
  text · date 비교는 refresh 로 사본을 다시 뜬 문서를 거른다.
- [판단] 확실하지 않은 행을 지금 원본으로 채우면, 이미 바뀐 영역을 「만들 때 값」으로 굳힌다. 비워 두면 예전 동작이 그대로라 잃는 것이 없다.

## 대안

- **사본 없이 영역 변경을 `stale` 로만 잡는다.** 축 변경(S7)과 상황(G1)을 못 푼다. 축은 원 설정이라 근거 원본이 아니다.
- **원이 축을 바꾸면 옛 영역을 새 축으로 옮긴다.** 5영역 → 2축은 대응이 하나로 정해지지 않는다. 지어낸 배치가 된다(ADR-024 결정 4).
- **채우기를 지금 원본으로 다 채운다.** 위 근거의 마지막 줄. 안 했다.
- **「다시 확인」 문서를 확정 · 내보내기에서 막는다.** 예전 동작을 바꾸는 일이라 PM 이 정한다. 이 ADR 은 막지 않는다.

## 되감기

옛 코드로 되감은 동안 교사가 관찰 기록의 **영역 · 상황만** 고치면 옛 코드는 `stale` 을 붙이지 않는다(사실 · 날짜만 본다).
다시 올라와도 이미 채워진 사본은 그대로라, 바뀐 기록을 쓴 문서가 `stale=false` 로 남는다. 시작할 때 코드로 막으려면
매 배포마다 전체 사본을 대조해야 해서 하지 않는다.

**다시 올라온 배포 뒤 한 번** 사본과 원본을 다시 대조한다. 새 코드가 기록을 고칠 때 쓰는 비교(`stale.observation_changed`)를
사본이 있는 관찰 기록마다 돌리고, 그 문서를 근거로 쓴 문서까지 `stale` 로 바꾼다. 다시 돌려도 된다.

```
docker compose exec backend python scripts/recheck_observation_snapshots.py           # 몇 건인지만
docker compose exec backend python scripts/recheck_observation_snapshots.py --apply   # 저장
```

되감은 적이 없으면 돌리지 않아도 된다 — 새 코드는 고칠 때마다 이미 같은 비교를 한다.

## 결과

- 마이그레이션은 열 셋을 더하기만 한다. 옛 코드는 새 열을 모르고 NULL 로 넣는다 — ADR-073 의 되감기(마이그레이션 PR 하나)를 지난다.
  되감은 동안 옛 코드가 만든 문서는 「다시 확인」으로 남는다. `backfill` 은 다시 돌려도 빈 칸만 채운다.
  열이 남는다고 내용까지 맞지는 않는다 — 아래 「되감기」.
- `GET /api/documents/{id}` 의 `sources[]` 에 `context` 가, 문서에 `observation_axis` 가 더해진다. `domain` 은 사본이다(없으면 원본).
- 영역 · 상황만 고쳐도 그 기록을 쓴 문서와, 그 문서를 근거로 쓴 문서가 `stale` 이 된다. 다시 검토할 문서가 늘어난다.
- 일일 · 주간 보육일지의 사본은 바뀌지 않는다. 일과 기록의 시간 · 이름 · 활동계획은 여전히 원본에서 읽는다 — 이 ADR 밖이다.
- 화면 미리보기는 상세 응답의 `sources[].domain` 을 쓰는 변경(`refactor/observation-screen-bugs` F12)이 들어가면 사본을 따른다.
  상황을 미리보기에 붙이는 일과 축(`observation_axis`)으로 행을 고르는 일은 그 뒤에 한다.
