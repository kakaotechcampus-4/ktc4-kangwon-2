# ADR-042: 연간계획안 v2 — 공통 계약 위에 형식별 세부 계약을 둔다 (월별 주제형 · 놀이 프로젝트형)

- 날짜: 2026-10-24 (결정 2026-10-23 하민)
- 상태 — **제안 (검토 전)**. 저장 · API 이름은 담당자 협의 전 제안이다.
- 관련 — ADR-030 PM-03 · PM-04 · ADR-032 · ADR-035 · ADR-038 · ADR-041 · `p0-planning/data/curriculum/nuri_curriculum_content_v0_1_0_draft.json`

## 맥락

[인터뷰] 현장 교사 피드백: 놀이 중심 원은 「월별 주제」가 아니라 「기간별 놀이 프로젝트」로 연간을 쓴다.
[실측] 받은 연간 레퍼런스(HWP)의 표는 시기 · 놀이명 · 지원매체 · 내용 및 지원 방향 예상하기 · 놀이를 통한 배움(영역별 내용범주) 5열이다. 3~5 / 6~8 / 9~11 / 12~2월 4구간, 구간마다 5개 놀이(병합 셀 기준 20개)가 있다.
[실측] 지금 연간 계약은 「3월 → 다음 해 2월 12개월, 달마다 Theme Reference 의 주제 1개」다(`YearlyPlan` · `YearlyPeriod`, 연간 Golden). 놀이 프로젝트형은 이 틀에 들어가지 않는다 — 달이 아니라 여러 달 구간이고, 칸이 주제 1개가 아니라 놀이 행 여러 개다.
[실측] 기관 자료의 구간 · 놀이 수는 원마다 다르다(예: 한 원의 만 5세 연간은 7/6/4/4). 「5개」는 레퍼런스의 실측값이지 현장 공통값이 아니다.
[실측] Backend 는 반당 연간 하나(`uq_plans_annual_per_classroom`)를 `plans.body` JSONB 로 저장하고, 월간 생성은 부모를 `YearlyPlan` 으로 읽는다(`monthly_router.py` · `generate_monthly_plan.py`).

## 결정

### 1. 연간 v2 = 공통 계약 + 형식별 세부 계약

연간계획안은 `format` 하나를 가진다. 공통 계약은 모든 형식에 같고, 칸 구조 · 생성 범위 · 검사는 형식별 세부 계약이 정한다.

| 형식 | 세부 계약 | 하위 계획(월간) |
|---|---|---|
| `MONTHLY_THEME` | 지금의 연간 계약 그대로(12개월 · Theme Reference 주제 · ADR-041 소주제 · 안전교육 입력) | 지금처럼 연결 |
| `PLAY_PROJECT` | 아래 §3 | **아직 없음** — 연간만 먼저 만들고 월간 연결은 별도 결정 |

### 2. 공통 계약

- 머리: `plan_id` · `school_year` · `classroom_ref` · `target_ages`(ADR-038 연령 집합) · `status` · `format` · `format_version` · `audit`.
- 소유: 반당 연간 하나. 형식은 만들 때 고른다. 기존 확정본을 다른 형식으로 바꾸거나 지우지 않는다.
- 상태: AI 생성은 `DRAFT` 로 시작한다. 명시적 `ActorId` 로만 `CONFIRMED` 가 된다. 확정 재호출은 200(ADR-035). 확정본은 읽기 전용이고 확정 취소는 없다(PM-03).
- 칸: 편집 가능한 값은 모두 `PlanItem`(값 · 근거 · 생성 방식 · 이력)이고 안정 주소(`item_id` + 형식이 정한 의미 주소)를 가진다. 표시 순서 · 이름을 바꿔도 주소는 그대로다.
- 생성: Rule 이 범위를 정하고 LLM 이 그 안에서 정하고 Rule 이 검사한다(ADR-032). 검사에 실패하면 부분 저장하지 않는다. 실패를 Rule/mock 값으로 조용히 채우지 않는다.
- 근거 · 생성 방식 · 이력의 세 축은 지금 규칙을 그대로 쓴다. 교사 수정은 `TEACHER_EDITED` 이력으로만 남고 생성 방식을 덮지 않는다.
- 읽기 호환: `format` 이 없는 기존 연간은 `MONTHLY_THEME` 으로 읽는다. 기존 행을 고쳐 쓰는 migration 은 하지 않는다.
- 하위 gate: 월간 생성은 부모가 `CONFIRMED` 이고 **월간을 지원하는 형식**일 때만 진행한다. `PLAY_PROJECT` 부모로 월간을 요청하면 LLM 호출 · 저장 없이 4xx 로 거절한다(오류 코드 이름은 api-spec 협의).

### 3. `PLAY_PROJECT` 세부 계약 v0 (첫 판)

- 구간 구성은 **판 있는 설정**이다: `3~5월 · 6~8월 · 9~11월 · 12~2월`(12~2월은 다음 해 1 · 2월). 구간 구성 · 확정 5행은 레퍼런스 실측값이며 국가 기준이 아니다. 행 추가 · 삭제는 첫 판에 없다.
- **후보 10 · 선택 5**: AI 는 구간마다 서로 다른 놀이 후보 10개를 만든다(원마다 갖춘 자료가 달라 후보마다 필요한 자료가 다양하게 한다). 후보 10개는 DRAFT 에 저장하고 교사가 DRAFT 안에서 구간마다 **정확히 5개**를 고른다(선택 · 해제 · 순서 변경). 구간마다 5개가 선택돼야 확정할 수 있다. 확정본 · 내보내기에는 선택된 5개만 남고, 고르지 않은 후보는 변경 이력에만 남는다.
- 행마다 4칸: `play_name`(놀이명) · `materials`(지원매체) · `support_direction`(내용 및 지원 방향 예상하기) · `learning`(놀이를 통한 배움).
- 의미 주소: `play_project.<구간 키>.cand<n>.<칸>`. 구간 키는 시작 · 끝 월로 정한다(예: `m03_m05`). 후보 번호는 생성 순서이며 선택 · 순서 변경으로 바뀌지 않는다.
- `learning` 은 문장이 아니라 **누리과정 내용 ID 목록**(후보마다 2~3개)이다. ID 는 활성 누리과정 내용 Reference 안에서만 고른다. 표시는 서버가 그 Reference 원문으로 「영역 - 내용범주 - 내용」을 붙인다. LLM 은 영역 · 범주 · 내용 이름을 쓰지 않는다. 근거는 `CURRICULUM` · `source_id` = 내용 ID · `source_version` = Reference 판.
- 놀이명 · 지원 방향은 새 제안을 허용한다. 실제로 참고한 기관 자료가 있을 때만 `INSTITUTION_SAMPLE` 근거를 단다. 참고 자료가 없어도 활성 Curriculum Reference 가 있으면 생성할 수 있다. 참고하지 않은 사례 · 공식 출처를 근거로 달지 않는다.
- 지원매체는 원이 가졌다고 단정하지 않는다. 준비 후보로 쓴다.
- 지원 방향은 예상이다. 아이의 실제 관심 · 관찰 · 결과를 사실처럼 쓰지 않고, 특정 결과물 · 사용 방법을 필수로 정하지 않는다.
- 저장 전 자동 검사가 잡는 것: 후보 수 · 구간 · 빈 칸 · 표시 문자 정책 · 배움 ID 수와 범위 · 같은 이름의 놀이(같은 구간 안, 다른 구간에서 넘겨받은 이름과도) · 입력에 없는 날짜 · 요일 · 시각 · 교사 이름(주간과 같은 검사). 공휴일 · 기념일 이름은 허용한다.
- 자동 검사가 **잡지 않는 것**: 소재 · 방식이 비슷한 놀이의 중복, 발달 효과 단정, 실제 관찰 · 관심을 사실처럼 쓴 문장, 필수 결과물 지정. 이것들은 지시문과 교사 검토에 맡긴다 — 통과한 초안이 이 규칙을 지켰다는 보장은 없다.
- 판: P1 모델의 `layout_version`(`play-project-layout-v0.2.0`)이 공통 머리 `format_version` 자리다. 구간 구성 · 후보 수 · 선택 수가 바뀌면 판을 올린다. 저장 · API 에서 쓸 이름은 저장 계약에서 맞춘다.
- AI 초안은 모든 후보의 4칸을 채워야 저장한다. 교사가 비운 칸의 확정 조건은 편집 · 확정 단계 계약에서 정한다.
- 재생성은 세 가지 의도로 나눈다: 다른 놀이 제안 · 같은 놀이의 지원 확장 · 표현 다듬기. 다른 놀이 제안은 **고르지 않은 후보만** 새 후보로 바꾸고 고른 후보는 그대로 둔다. 나머지 범위 · 보존 규칙은 편집 · 재생성 단계 계약에서 정한다.
- Curriculum Reference 가 승인 전 · 없음 · 깨짐이면 생성 전에 막는다.

### 4. 누리과정 내용 ID 의 연령 경계 (후속 2026-10-26 하민)

- 누리과정 59개 내용 ID 는 연령별 허용 · 금지 목록으로 나누지 않는다.
- 활동 · 도구 · 재료의 연령 적합성과 안전 검사는 유지한다.
- 현재 동작과 일치하므로 코드 · Reference JSON · 승인 상태는 변경하지 않는다.

월간 v2 도 같은 경계를 따른다. 이 절은 위 「아직 정하지 않은 것」과 누리과정 내용 Reference 의 사람 승인을 대신하지 않는다.

[출처] 2019 개정 누리과정 해설서 PDF p.19 · 37 · 38 · 60 (인쇄 18 · 36 · 37 · 59): 59개 내용은 연령 구분 없이 3~5세가 모두 경험할 수 있는 내용으로 제시했고, 특정 교과 · 연령별 세부 내용으로 이해하지 않도록 한다. 폐지된 「3-5세 연령별 누리과정」의 세부 내용(해설서 부록 신구 대조표)은 연령 근거로 쓰지 않는다.

## 근거

[판단] 형식을 하나의 공통 껍데기와 세부 계약으로 나누면 기존 월별 주제형의 타입 · Golden · 저장을 바꾸지 않고 새 형식을 더할 수 있다. 기존 `YearlyPlan` 에 의미 없는 월별 주제를 채워 넣는 방법보다 검사가 정직하다.
[실측] 레퍼런스 배움 칸 32문장은 모두 고시문 59 내용 중 하나로 대응된다(29개는 문장 그대로, 3개는 문구 차이). 영역 · 범주 표기는 문서 안에서도 흔들린다 — ID 를 고르고 서버가 원문을 붙이면 이 흔들림이 사라진다.
[출처] 2019 개정 누리과정 고시문 p.10–14: 5 영역 · 15 내용범주 · 59 내용. 고시는 활동 · 주제 · 월별 배치를 정하지 않는다.
[판단] 「확정 5행」은 레퍼런스 값을 첫 판 설정으로 둔 것이다. 원마다 다르다는 실측이 있어 판을 올려 바꿀 수 있게 둔다.
[판단] 후보를 5개만 주면 원에 없는 자료가 필요한 놀이를 교사가 피할 방법이 재생성뿐이다. 후보 10개 중 고르게 하면 한 번의 호출로 원 사정에 맞출 수 있다. 출력이 약 2배라 구간당 비용이 약 2배다.

## 대안

- 기존 `YearlyPlan` 에 구간 · 행을 덧붙이기: 12개월 · 월 주제 1개 불변식과 연간 Golden 이 깨지고 월간 연결이 우연히 동작한다. 하지 않는다.
- 반당 두 형식 동시 보유: 유일 인덱스 · 조회 · 월간 부모 선택이 모두 바뀐다. 필요가 확인되면 다시 본다.
- 배움 칸을 자유 문장으로 생성: 공식 명칭을 LLM 이 쓰게 되어 표기 오류 · 없는 범주가 생긴다. 하지 않는다.
- 처음부터 월간까지 함께: 받은 월간 레퍼런스는 구역(주제선정이유 · 예상 놀이 방향 · 주차별 생활/안전 · 시간표 · 안내)이 많고 연간 놀이명과 문자열이 일치하지 않는다. 연간을 먼저 검증한다.

## 결과

- 기존 연간(`MONTHLY_THEME`)의 Core 타입 · 연간 Golden · 승인 데이터 SHA · API 응답은 바뀌지 않는다.
- `PLAY_PROJECT` 는 새 aggregate · 새 Golden 으로 더한다. 첫 시제품은 3~5월 한 구간 후보 10개 생성 · InMemory 저장이다. 후보 선택 · 편집 · 재생성 · 확정은 다음 단계에서 더한다.
- 누리과정 내용 Reference 는 사람 검토 · 승인 뒤에만 런타임에서 쓴다. 승인 상태와 `runtime_active` 가 어긋난 자료는 읽을 때 거절한다.
- LLM 응답은 스트리밍으로 받는다(후보 10개가 비스트리밍 출력 상한을 넘는다). 오류 조각 · 종료 표시 없음 · 정상 종료(`stop`)가 아닌 응답은 JSON 이 맞아도 저장하지 않는다. 지금 timeout 은 읽기 한 번의 상한이지 전체 처리 시간 상한이 아니다 — 전체 마감 시간은 backend 연결 전에 정한다.
- 이 결정이 채택되면 루트 · `p0-planning` `CLAUDE.md` 의 연간 계약 절을 「월별 주제형 세부 계약」으로 고쳐 적는다.
- 아직 정하지 않은 것: 저장의 형식 구분 위치(본문 필드 · 열) · API 경로와 오류 코드 · 전체 연간 LLM 호출 단위 · 다개월 자료 검색 계약 · 월간 연결 · 후보 선택을 남길 변경 이력 이벤트 모양.

## 후속 결정 — 후보 선택 · 편집 · 확정 (2026-10-26 하민)

위 「아직 정하지 않은 것」 중 **후보 선택을 남길 변경 이력 이벤트 모양**을 정한다. 범위는 Core(`p0-planning`)이고, 저장 API · 화면 연결은 다음 단계다.

- **선택 상태**: 구간마다 고른 후보의 `row_key` 를 문서 배치 순서대로 둔다(`PlayPeriodRows.selected`). 후보 배열은 지우거나 다시 정렬하지 않는다 — 미선택 후보의 값 · 주소 · 이력이 그대로 남는다.
- **새 Audit 이벤트 `CANDIDATES_SELECTED`**: 계획안 단위. 누가(교사 `actor_id`) · 언제 · 어느 구간(`period_key`) · 고른 후보 ID 의 저장 전 · 후(배치 순서). 교체 · 추가 · 빼기 · 순서 변경이 모두 구별된다. `TEACHER_EDITED` 에 섞지 않는다 — 기존 네 이벤트의 의미는 바뀌지 않는다.
- **기록 단위**: 선택 저장 1번. 실제로 바뀐 구간마다 이벤트 1개. 같은 선택 · 순서를 다시 저장하면 이벤트도 쓰기도 없다. 여러 구간을 한 번에 저장하면 모두 검사한 뒤 한꺼번에 적용한다 — 한 구간이라도 틀리면 아무것도 남기지 않는다.
- **중간 저장**: DRAFT 는 구간마다 0~5개를 저장할 수 있다. 확정은 레이아웃의 모든 구간이 정확히 5개일 때만 된다. 확정에는 교사 `actor_id` 가 필요하고, 확정 뒤에는 선택 · 편집이 막힌다.
- **편집**: 고른 후보의 놀이명 · 지원매체 · 지원 방향만 고칠 수 있다(`TEACHER_EDITED`). 배움 칸은 누리과정 원문을 서버가 그리는 칸이라 글자 편집을 받지 않는다 — 허용 ID 를 다시 고르는 기능은 후속이다. 고친 후보를 선택 해제해도 값 · 이력은 남고, 다시 고르면 그대로 보인다.
- **저장 호환**: 새 칸(`selection_change`, `selected`)은 기본값이 있어 옛 본문이 그대로 읽힌다(마이그레이션 없음). 다만 선택이 저장된 계획안은 **이전 판 서버가 읽지 못한다**(모르는 이벤트 값) — 이 판을 배포한 뒤 되돌릴 때 주의한다.
- **후속으로 미룬 것**: 「다른 놀이」(미선택 후보만 교체). 그때 LLM 실패 시 기존 후보 보존 · 중복 회피 범위 · 교체 이력 · 새 후보 주소를 정하고, **편집한 뒤 선택 해제된 후보**를 교체할지 · 보존할지를 다시 정한다. 연결 전까지 화면의 버튼은 숨기거나 끈다.
