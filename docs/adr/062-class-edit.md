# ADR-062: 반 정보를 고칠 수 있게 한다 — 아이가 있으면 동의를 끌 수 없고, 연령은 알리기만 하고, 확정한 계획안은 그때의 반 이름을 지킨다

- 2026-11-04
- 상태 — 채택
- 보충 — ADR-010 · ADR-004 · ADR-038

## 맥락

지금은 반을 만든 뒤에 고칠 수 없다. 반 수정 API 가 없고(`docs/api-spec.md` §2 끝에 「수정은 P1」로만 적혀 있었다),
화면은 로컬 사본이 바뀌면 「등록한 반 정보 수정은 아직 지원하지 않아요」를 던진다(`frontend/lib/api/onboarding.ts:171-175`).
**동의 체크박스를 건너뛰고 아동 명단 단계로 넘어간 교사가 돌아와 체크할 수 없다.**

2026-11-04 성진이 동의만 여는 안이 아니라 **반 정보 전체 수정**을 골랐다. 반을 고치면 흔들리는 것은 이렇다.

| 고치는 칸 | 확정 계획안 내보내기 | 이미 쓴 일지 | 새 월간 · 주간 |
|---|---|---|---|
| 반 이름 | **새 이름으로 바뀐다** ⚠ (`klass.name` 을 그때 읽는다) | 제목 · 내려받은 파일은 옛 이름. 상세 화면의 반 표시는 새 이름 | 새 이름 |
| 연령 | 옛 연령 그대로(스냅샷) | 해당 없음 | **옛 연령을 이어받는다** ⚠ (부모 연간 계획안의 연령) |
| 담임 이름 | 찍는 곳 없음 | 찍는 곳 없음 | 찍는 곳 없음 |
| 동의 | 영향 없음 | 영향 없음 | 영향 없음 |

## 결정

1. **`PATCH /api/classes/{class_id}`** 가 `name` · `age_min`+`age_max` · `teacher_name` · `consent_confirmed` 를 고친다.
   **보낸 칸만 바꾼다.** 원 정보 PATCH 와 같다(`extra="forbid"` · `null` 은 안 보냄). `{}` 는 아무것도 바꾸지 않고 200 이다.
2. **`age_min` 과 `age_max` 는 같이 보낸다.** 하나만 보내면 422. 3~5 · `age_min <= age_max`(ADR-038).
3. 그 밖의 칸(`child_count` · `school_year` · `teacher_id` …)은 422. 원아 수는 입력하는 화면이 없어 고치지 않는다.
4. **권한은 반 단위 공통 규칙이다.** 쓰기는 OWNER · OPEN 만. 같은 원 승인 없음 403 `CLASS_ACCESS_REQUIRED`,
   승인된 교사 403 `CLASS_READ_ONLY`, 다른 원 · 없는 반 404.
5. **이름이 겹치면 409 `ALREADY_EXISTS`**(`fields: ["name"]`). 생성과 같이 DB 제약이 터진 것을 바꾼다.
6. **동의** — `true` 는 `consent_confirmed_at` 이 비었을 때만 지금 시각을 넣고, 이미 있으면 처음 시각을 둔다.
   `false` 는 `null` 로 되돌린다. **다만 아동이 1명 이상이면 409 `GATE_BLOCKED`(`fields: ["consent_confirmed"]`)이고
   그 요청에서 바뀌는 것은 없다.** 같이 보낸 다른 칸도 적용하지 않는다. 아동 0명이면 끌 수 있다.
   **반대 방향도 막는다 — 동의 확인 전인 반에는 아동 추가(`POST /api/classes/{class_id}/children`)가 409 `GATE_BLOCKED`
   (`fields: ["class_id"]`)다.** 두 경로는 같은 반 행을 잠근 뒤 검사한다.
7. **연령은 막지 않고 알린다.** 이미 만든 계획안은 만들 때의 연령을 지킨다. 화면이 저장에 성공한 뒤,
   연령이 바뀌었고 그 반에 연간 계획안이 있으면 기존 `Notice` 로 알린다. 서버 응답에 따로 알리는 칸은 없다.
8. **확정한 계획안은 확정할 때의 반 이름 · 담임 이름을 지킨다**(ADR-010 결정 1 보충). 확정으로 바뀌는 순간
   `plans.class_name` · `plans.teacher_name` 에 찍고, DB 가 「확정 행이면 둘 다 있다」를 검사한다. 확정을 취소했다가
   다시 확정하면 그때 값으로 다시 찍는다 — 반 이름 오타를 고친 뒤 계획안에 반영하는 길이다.
   **계획안은 아직 아니라서**(내보내기가 지금 반 이름을 읽는다) 열을 더하고, 이미 확정된 계획안은 지금 반 값으로 채운다.
   일지는 제목과 내려받은 파일이 만들 때 이름을 이미 지킨다.
   일지 상세의 반 표시(`class_name`)는 어느 반 기록인지 보여 주는 칸이라 지금 반 이름으로 둔다.
9. `teacher_name` 은 화면에 보이는 글자다. 반 주인(`teacher_id`)은 바뀌지 않는다.
10. **이력 테이블을 두지 않는다.** 동의는 `consent_confirmed_at` 하나만 남긴다.
11. 응답은 200 이고 `GET /api/centers/{center_id}/classes` 의 item 과 같다(`my_access` 포함).
12. **PR 은 네 개, 순서가 있다.** ① 계약(이 문서) → ② 계획안 반 이름 · 담임 이름 사본 + 기존 확정 행 채우기 → ③ PATCH API → ④ 온보딩 화면(수정 포함).
    **② 가 ③ 보다 먼저 머지된다.**

## 근거

- **[실측]** 계획안 내보내기는 반 이름을 살아 있는 값으로 읽는다 — `backend/app/features/plans/export.py:118` · `:236-240`.
  놀이 중심 월간만 만들 때의 이름을 갖는다(`display.class_name`, `p0-planning/src/ssuksak/planning/application/generate_play_monthly_plan.py:530`).
- **[실측]** 일지는 제목을 만들 때 고정한다 — `backend/app/features/documents/router.py:373`.
  상세 응답의 `class_name` 은 지금 반 이름을 읽는다 — `documents/router.py:208`.
- **[실측]** ADR-010 결정 1 이 「반 이름·연령·담임·학년도를 스냅샷한다」고 정했다(`docs/adr/010-initial-schema.md:15-16`, 근거 `:28-32`).
- **[실측]** 서버는 아동을 추가할 때 동의를 검사하지 않는다 — `backend/app/features/children/router.py:49-86`.
  ADR-004 는 명단을 동의 확인 뒤에만 받는다고 했으므로, 아이가 있는데 동의를 끄면 「이름은 있는데 동의 없음」이 남는다.
  끄기만 막으면 반대 길이 열려 있다 — 아동 0명일 때 동의를 끈 뒤, 옛 화면을 띄운 기기가 아동을 넣으면 서버가 받아 준다
  (아동 추가는 반 행을 잠그지만 동의를 보지 않는다, `children/router.py:60-65`). 그래서 추가 쪽에도 같은 검사를 둔다(2026-11-04 Codex 검토).
- **[실측]** 아동을 지우는 길은 안 된다 — 관찰 기록(`backend/app/features/observations/models.py:77`)과 일지(`backend/app/features/documents/models.py:54`)가 아동을 참조한다.
- **[실측]** 새 월간 · 주간은 부모 연간 계획안의 연령을 이어받는다 — `p0-planning/src/ssuksak/planning/application/generate_monthly_plan.py:451`(ADR-038).
- **[실측]** 반 이름을 바꾼 코드가 지금까지 없다 — 마이그레이션 · 스크립트에 `UPDATE classes` 가 없다(2026-11-04 확인).
  그래서 이미 확정된 계획안의 사본을 오늘의 `classes.name` · `teacher_name` 으로 채워도 잃는 것이 없다. **이는 PATCH API 가 아직 없는 동안만 참이다.** ② 가 ③ 보다 먼저인 까닭이다.
- **[실측]** 낡은 화면이 옛 값을 되쓸 수 있다 — `loadServerClasses`(`frontend/lib/api/onboarding.ts:378-404`)는 연령과 저장된 서명을 새로 고치지 않는다.
- **[판단]** 학년도마다 반은 새 행이라 학년 중간에 연령을 바꾸는 일은 드물다. 막기보다 알린다. (성진 2026-11-04)
- **[판단]** 이력은 보여 줄 화면이 없다. 만들어 두면 낡는다. (성진 2026-11-04)
- **[판단]** 사본은 만들 때가 아니라 확정할 때 찍는다. ADR-010 은 「생성 시점」이라 적었지만 막으려던 것은 확정한 제출 문서가
  바뀌는 것이다(`:28-32`). 내보내기는 확정본만 된다(`backend/app/features/plans/export.py:6`) — 확정 때 찍어도 그 목적이 지켜지고,
  오타를 고칠 길(확정 취소 → 다시 확정)이 남는다. (성진 2026-11-04)
- **[판단]** 담임 이름은 지금 찍는 계획안 문서가 없지만 ADR-010 대로 같이 사본을 둔다. (성진 2026-11-04)

## 대안

- **연령 — 계획안이 있으면 막기.** 초안 연간은 지우고 다시 고칠 수 있지만, 확정한 연간이나 월간이 딸린 연간은
  지울 수 없어(`backend/app/features/plans/router.py:616` · `:633`) 그 반은 연령을 영영 못 고친다. 안 골랐다.
- **연령 — 계획안 화면을 열 때마다 경고.** 세 화면에서 반 연령과 계획안 연령을 비교하는 코드가 생기고,
  다른 기기의 브라우저 사본이 낡아 있으면 틀린 경고가 뜬다. 저장 직후 한 번 알리는 쪽이 단순하다.
- **동의 — 끄게 두고 아이는 그대로.** ADR-004 와 어긋난다.
- **동의 — 끄기만 서버가 막고 아동 추가는 지금처럼 화면만 막는다.** 바꿀 코드가 적지만, 옛 화면을 띄운 기기에서
  「이름은 있는데 동의 없음」이 생긴다. 안 골랐다.
- **동의 — 끄면 아이를 지운다.** 그 아이를 참조하는 관찰 기록 · 일지가 깨지고 되돌릴 수 없다.
- **반 이름 — 다음 내보내기부터 새 이름.** 확정해 제출한 문서가 소급해 바뀐다. ADR-010 결정 1 을 뒤집어야 한다.
- **반 이름 사본 — 만들 때 찍기.** ADR-010 문구 그대로고 고칠 곳이 한 곳이지만, 오타를 고쳐도 이미 만든 계획안에 반영할 길이 없다.
- **반 이름 사본 — 본문 JSON 안에.** 본문은 저장할 때마다 통째로 다시 써져서(`backend/app/features/plans/repository.py:52-53` 의
  `import_source` 처럼) 매번 살려 두는 코드가 필요하고, DB 가 검사할 수 없다.
- **동의만 먼저 여는 안.** 사용자가 전체 수정을 골랐다.

## 결과

- 계약은 `docs/api-spec.md` §2 「반 수정」, 요구사항은 FR-108, 화면은 `docs/screen-spec.md` S10 「반 관리」다.
  **서버 · 화면은 아직 없다**(구현 전).
- **아동 추가 계약(`docs/api-spec.md` §2-1)이 바뀐다.** 동의 확인 전 반이면 409. 서버 검사는 PR ③ 에 들어간다.
  운영 DB 에 동의 없이 아동이 들어간 옛 반이 있으면, 그 반은 동의를 체크해야 아동을 더 넣을 수 있다.
- **PR ②(계획안 반 이름 · 담임 이름 사본 + 기존 확정 행 채우기)가 PR ③(PATCH API)보다 먼저 머지된다.** 거꾸로면 이름이 바뀐 반의 옛 계획안을 새 이름으로 채우게 된다.
  `docs/schema.md` 불변 규칙 2 는 PR ② 가 「확정 시점」으로 고친다.
- **FE 규칙(PR ④)** — 수정은 저장 버튼에서만 보낸다. `syncClass` 는 만들기 전용으로 남겨, 그걸 부르는 다른 화면은 PATCH 를 보내지 않는다.
  저장 뒤에는 응답으로 브라우저 사본과 서명을 다시 쓴다.
- 다른 기기의 사이드바 · 상단 바는 브라우저 사본을 보여 주므로 늦게 바뀐다. 후속으로 둔다.
