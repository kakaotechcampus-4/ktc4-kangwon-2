# ADR-029: 같은 원 교사는 1회용 초대 코드로 들어온다

- 2026-10-10
- 상태 — 채택
- 관련 — ADR-017(인가는 원 단위까지) · api-spec §1 · §1-1 · #103

## 맥락

온보딩 1단계 `POST /api/centers` 는 원을 새로 만들고 그 교사의 `users.center_id` 를 채운다.
같은 원의 두 번째 담임은 기존 원에 들어갈 길이 없어서, 원을 하나 더 만들게 된다 — 반 · 계획안 ·
평가제 체크가 원 두 개로 갈라진다. `users.center_id` 구조는 이미 원 하나에 교사 여럿을 허용한다.

## 결정

1. **원에 속한 교사가 코드를 만들고, 원이 없는 교사가 그 코드로 들어온다.** `center_invites` 테이블.
2. **1회용 · 7일 만료.** 쓰면 `used_by` · `used_at` 을 남기고 다시 못 쓴다.
3. **코드는 `secrets` 로 만든 10자**(헷갈리는 0·O·1·I·L 을 뺀 31자). 교사가 단톡방에서 보고 옮겨 적는다.
4. **없는 · 쓴 · 만료된 코드는 같은 404 다.** 이미 원이 있으면 §1 과 같은 409.
5. 목록 · 취소 · 내보내기(탈퇴) API 는 만들지 않는다.

## 근거

- **[판단]** 들어온 교사는 그 원의 아동 실명 명단을 본다(ADR-017 — 인가가 원 단위다). 오래 살아 있는
  코드가 단톡방에 남으면 퇴사자 · 외부인이 들어올 수 있다. 1회용 · 만료가 가장 적은 코드로 막는다.
- **[판단]** 31^10 ≈ 8×10^14 개라 7일 안에 맞혀 볼 수 없다. 404 를 하나로 합쳐 맞혀 보는 쪽에 힌트를 주지 않는다.
- **[판단]** 이메일 초대는 메일 발송 의존이 새로 생긴다. 코드는 교사가 직접 전한다.

## 대안

- **원 이름 검색 후 가입 요청 · 원장 승인.** 승인 화면과 역할(원장/담임)이 먼저 있어야 한다. 아직 없다.
- **원마다 고정 코드 하나.** 재발급 · 폐기 규칙이 따로 필요하고, 새어 나가면 계속 열려 있다.
- **이메일 초대 링크.** 외부 메일 의존이 생긴다. 「부가 기능이 죽어도 본 기능은 돈다」에 어긋난다.

## 결과

- `center_invites` 테이블이 늘었다(마이그레이션 하나).
- 코드를 받은 사람은 누구든 그 원에 들어간다 — **코드를 아는 것이 곧 권한이다.** 역할 · 승인이 생기면 다시 본다.
- 원을 나가거나 다른 원으로 옮기는 길은 아직 없다(409 그대로).
- 화면은 연결 정보를 브라우저에 두는 구조라, 들어온 교사의 온보딩 2단계에는 **다른 교사가 만든 반이 보이지 않는다.**
  자기 반만 새로 만든다. 서버 `GET /classes` 는 원의 모든 반을 돌려준다.
