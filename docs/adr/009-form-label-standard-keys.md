# ADR-009: 양식 라벨은 DB 컬럼이 아니라 표준 개념 키로 정규화한다

- 날짜: 2026-09-11
- 상태 — 채택

## 맥락

`forms` 기능은 hwp/hwpx 양식에서 표와 라벨을 추출한다. 어린이집마다 같은
개념을 다른 문구로 쓴다 (`docs/structure.md`: forms 는 "없음(hwp 양식 파싱,
DB 미사용)" 으로 명시돼 있다). 이 라벨을 다운스트림(`plans` 등)이 쓰려면
정규화가 필요한데, `plans` 의 DB 스키마는 아직 확정되지 않았다.

## 결정

라벨 문구 -> **표준 개념 키**(`topic`, `activity`, `month` 등) 매핑표를
`resources/forms/label_mapping.json` 에 코드와 분리해 둔다. 표준 키는
`plans` 의 실제 DB 컬럼명이 아니다. `plans` 등 다운스트림이 표준 키를 자기
컬럼에 어떻게 연결할지는 그쪽에서 정한다. `forms` 는 "라벨 문구 -> 표준 키"
변환까지만 책임진다.

## 근거

- **[판단]** `plans` 스키마가 아직 정착되지 않아, 스키마에 직접 의존하면
  스키마가 바뀔 때마다 `forms` 도 같이 고쳐야 한다. 표준 키라는 중간 계층을
  하나 두면 두 기능이 독립적으로 바뀔 수 있다.
- **[판단]** `docs/structure.md` 의 "forms 는 DB 미사용" 규칙과 정합성을
  맞추려면, forms 가 특정 기능의 DB 컬럼명을 알아서는 안 된다고 봤다.
- **[실측]** 실제 hwp 연간계획안 파일로 검증. 라벨 83개(중복 제거 80개) 중
  헤더 라벨 3개(`월`·`주제`·`예상놀이`)만 정확히 매핑되고, 나머지 데이터
  값(월 숫자·주제 내용 등)은 매핑되지 않음 — 오탐 없음.

## 대안

- **`plans` 스키마 확정을 기다린다** — 이번 주 일정상 채택 안 함. 매핑
  로직은 스키마와 느슨하게 결합돼 있어 나중에 표준 키 이름만 조정하면 된다.
- **라벨을 `plans` DB 컬럼명으로 직접 매핑** — 기각. `forms` 가 다른 기능의
  스키마를 알게 되어 `docs/structure.md` 의 기능 소유 규칙(다른 feature 를
  직접 참조하지 않는다)과 어긋난다.
- **매핑 규칙을 파이썬 dict로 코드에 하드코딩** — 기각. `docs/structure.md`
  의 "데이터를 코드에 하드코딩하지 않는다" 규칙 위반.

## 결과

- `plans` 등 다운스트림은 `label_map` 의 표준 키(`null` 아닌 것만)를 받아
  자기 컬럼에 매핑하는 어댑터를 따로 짜야 한다.
- 새 양식에서 처음 보는 표현이 나오면 `label_mapping.json` 에 alias 한
  줄만 추가하면 된다. 코드 배포는 필요 없지만, 매핑표는 프로세스 시작 시
  한 번만 읽고 캐시하므로(`mapping.py` 의 `lru_cache`) **서버 재시작은
  필요하다.**
- 표준 개념 키 목록(13개)은 초안이다. 팀 리뷰에서 개념 추가·삭제가 나올 수
  있다.
