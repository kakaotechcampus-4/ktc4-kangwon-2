# ADR-081: 생성 요청 하나가 LLM 을 부르는 횟수를 48번으로 막는다

- 날짜: 2026-11-09
- 개정: 2026-11-10 — 8 → 48, 스레드로 나뉜 호출을 합쳐 센다, 전용 오류 `LlmCallCapExceeded` (PR #466 리뷰 반영)
- 상태: 채택 (2026-11-11 구현 확인 — `MAX_LLM_CALLS_PER_RUN = 48`, `backend/app/shared/llm/client.py:63`)

## 맥락

[실측] 생성 요청 하나가 LLM 을 몇 번 부르는지는 `ssuksak.timing` 의 run 이 센다(`backend/app/shared/llm/client.py` `_llm_call`).
세기만 하고 막지는 않았다.

[실측] 2026-11-09 ADR-076 「모델에 닿지 못한 LLM 요청만 한 번 더 보낸다」가 들어오면서
시도마다 `_llm_call` 을 따로 지나 호출 수가 시도마다 오른다. 수리 1회와 재시도 1회가 겹치는 경로가 생겼고,
반복문이 새면 요청 하나가 끝없이 부를 수 있는데 그걸 막는 장치가 없다.

월 예산 카운터(70% 경고 · 90% 차단)는 2026-09-21 무효가 됐다(CLAUDE.md 「LLM 예산」) — 파일럿 중 교사 앞에서 서비스가 멈추면 안 되고,
사용량은 담당자가 본다.

처음 안(상한 8)에는 구멍이 둘 있었다. 리뷰에서 확인했다(2026-11-10).

1. [실측] **상한이 스레드마다였다.** 놀이형 연간(ADR-077)은 구간 4개를 `ThreadPoolExecutor` 로 동시에 부른다. `timing.in_thread` 가
   스레드마다 새 작업자를 만들고 호출 수를 0 에서 따로 세다가 작업이 끝날 때 요청의 수에 더했다. 그래서 요청 하나가 아니라
   **스레드 하나**가 8 이었다 — 반복문이 샌 요청이 스레드 수만큼 더 부를 수 있었다.
2. [실측] **설계상 최대가 8 이 아니라 24 였다.** ADR-077 이 들어오며 놀이형 연간은 첫 호출 4 + 실패한 구간 다시 ≤4 + 겹친 후보 다시 ≤4 = 논리 호출 12번이고,
   호출마다 ADR-076 의 전송 재시도가 한 번씩 붙어 시도는 24번이다. 8 로 두었으면 정상인 최악 경로가 운영에서 `GENERATION_FAILED` 로 끝났다.

## 결정

1. **생성 요청 하나(timing run) 안에서 LLM 호출 시도는 48번까지다.** 49번째는 부르지 않는다. 재시도도 센다. 막힌 시도는 세지 않고 `llm_call` 줄도 남기지 않는다.
2. **스레드를 합쳐서 센다.** 세는 곳은 요청의 `Run` 하나다. `timing.in_thread` 로 열린 작업자는 그 `Run` 을 가리킬 뿐 자기 수를 갖지 않는다(작업자가 또 스레드를 열어도 같다).
   검사와 증가는 `timing.reserve_llm_call(limit)` 이 한 락 안에서 한다 — 스레드 여럿이 동시에 와도 합이 상한을 넘지 않는다. 상한 값은 backend(`client.py`)가 쥐고 p0-planning 은 받아서 비교만 한다.
3. **48 은 정책 값이고 설계상 최대(24)의 2배다.** 같게 두면 다음에 정상 경로를 하나 더하는 변경이 운영에서 조용히 500 이 된다. 상한의 일은 반복문이 새는 것을 막는 것이지 정상 경로를 재는 것이 아니다.
   **생성 오케스트레이션의 최악 경로는 CI 테스트가 지킨다** — `test_play_project_llm_cap.py` 가 `play_project.generate` 를 끝까지 돌려 최악 경로(네 구간 모두 실패 · 모두 겹침 · 모든 시도의 첫 전송이 끊김)가 정확히 24번이고 상한 안에서 계획안이 나오는지 본다.
   모델 자리의 provider 와 소켓을 여는 안쪽만 가짜라, 실제 어댑터 · SSE · DB 저장(라우터)은 이 테스트 밖이다.
   경로가 늘어 이 숫자가 바뀌면 테스트가 먼저 깨지고, 그때 아래 표와 이 값을 같이 고친다.
4. **전용 오류 `LlmCallCapExceeded(LlmFailed)`.** `app.shared.llm` 에서 내보낸다. `LlmFailed` 의 하위라 계약은 그대로다 — 라우터가 `LlmFailed` 로 잡는 곳은 모두 `isinstance` 로 거르므로
   `GENERATION_FAILED`(500, 「다시 시도」)로 같이 간다. `_NotDelivered` 가 아니라서 `_once_more` 는 다시 보내지 않는다.
5. **끝난 실패로 다룬다.** 놀이형 연간(`play_project.py`)은 상한 오류를 (a) 실패한 구간을 한 번 더 부르는 대상에서 빼고(원인 사슬 어디에 있어도), (b) 겹친 후보를 다시 만들다 만났을 때
   경고만 남기고 원래 후보로 잇지 않고 그대로 올린다. 그 밖의 오류는 ADR-077 대로 경고하고 잇는다. 상한을 넘은 요청이 다시 부르거나, 막힌 걸 삼키고 다른 오류(`DUPLICATE_PLAY_NAME`)로 바뀌어 끝나면 원인을 못 찾는다.
6. **한 줄을 남긴다.** 상한에 걸리면 `timing_logger` 에 `llm_cap_hit run=<id> kind=<kind> used=<n> limit=<n>` 한 줄(WARNING). 숫자와 이름뿐이고 프롬프트 · 응답은 없다(CLAUDE.md §21 · ADR-004).
   막힌 순간의 `used` 는 `limit` 과 같다. 요청이 끝날 때 `plan_timing` 줄의 `llm_calls=<n>` 이 합계를 준다.
7. `post_json` · `post_stream` 둘 다 걸린다. run 이 없는 호출은 걸지 않는다(아래 표).

## 근거

- **경로별 호출 수.** [실측] 코드 확인(2026-11-10). 논리 호출은 Application 이 부른 수이고, 전송 시도는 거기에 ADR-076 의 재시도(모델에 닿지 못했을 때만, 호출마다 최대 1회)를 더한 수다.
  상한이 세는 것은 **전송 시도**다.
  ```
  run kind         논리 호출                                              전송 시도(최대)
  annual_play      첫 호출 4 + 실패한 구간 다시 ≤4 + 겹친 후보 다시 ≤4       12 → 24
  annual_theme     post_json 2(12개월 주제 + 소주제)                         2 →  4
  monthly_theme    스트림 2(첫 호출 + 수리 최대 1)                           2 →  4
  monthly_play     스트림 2(첫 호출 + 수리 최대 1)                           2 →  4
  weekly           2(문서 단위 첫 호출 + 수리 최대 1)                         2 →  4

  run 없음(상한이 걸리지 않는다 — 센 실행이 없다)
  문서 초안(documents/draft)       1 → 2
  칸 재생성 · 주간                  2(첫 호출 + 수리 최대 1) → 4
  칸 재생성 · 월간                  1 → 2
  연간 가져오기 추출(annual_extract) 1 → 2
  jev 판정(문장 6개씩 묶음)         문서당 ≤6 → 12
  ```
  근거 줄: `plans/play_project.py` `generate` · `plans/router.py:455` · `planner/service.py` · `generate_play_monthly_plan.py` · `planner/weekly.py:949` · `planner/cell_service.py:42` · `application/weekly_lifecycle.py`(`RegenerateWeeklyPlanCell._llm`).
  놀이형 연간만 이 중 최대(24)다. 나머지는 4 이하라 48 에서 멀다.
- **월 예산 차단과 다르다.** [판단] 이 상한은 요청 하나 안에서 호출이 불어나는 것만 막는다. 월 합계는 세지 않고, 정상 요청은 막지 않는다.
  09-21 결정이 피하려던 「파일럿 중 서비스가 멈추는 일」은 생기지 않는다.
- **넘으면 버그다.** 설계상 최대의 2배이므로 49번째가 나가려 하면 어딘가 반복문이 샌 것이다(재시도가 재시도를 부르거나, 다시 부르기가 다시 부르기를 부르는 식).

## 대안

- **8(처음 안) · 24(설계상 최대와 같음)** — 8 은 정상인 놀이형 연간 최악이 막힌다. 24 는 정확하지만 경로를 하나 더하는 다음 변경이 테스트 없이 운영에서 500 이 된다. 같은 값이면 경고도 여유도 없다.
- **스레드마다 따로 세기(처음 안)** — 요청 하나의 폭주를 막지 못한다. 위 맥락 1.
- **작업이 끝날 때 더하기(처음 안)** — 도는 동안에는 합이 안 보여서 같은 이유로 못 막는다. 락 안에서 즉시 센다.
- **경로마다 다른 상한** — 경로가 바뀔 때마다 표를 같이 고쳐야 한다. 한 값으로 충분하다.
- **토큰 · 금액 상한** — 응답이 오기 전에는 출력 토큰을 모른다. 출력 상한은 `max_completion_tokens` 가 따로 있다.

## 결과

- 새 기능이 생성 요청 하나에서 LLM 을 더 부르게 되면 위 표를 고친다. 놀이형 연간의 최악이 바뀌면 `test_play_project_llm_cap.py` 가 먼저 깨진다. 48 에 가까워지면 이 값을 다시 정한다.
- 상한에 걸린 요청은 `llm_cap_hit` 줄과 `plan_timing` 줄의 `outcome=http_500` (`LlmCallCapExceeded`)로 보인다.
- `ssuksak.timing` 의 작업자는 호출 수를 따로 갖지 않는다. ADR-077 결정 6 의 「호출 수는 끝날 때 더한다」는 이 ADR 로 바뀐다(즉시 요청의 수에 쌓인다).
- 테스트 — `backend/tests/test_llm_call_cap.py`(경계 · 재시도 · 스트림 · 스레드 합산 · 로그 · 계약 코드) · `backend/tests/test_play_project_llm_cap.py`(놀이형 연간 최악 24번 · 상한에서 멈춤) ·
  `p0-planning/tests/unit/test_timing.py`(공유 카운터 · 동시성 · 실행 분리).
