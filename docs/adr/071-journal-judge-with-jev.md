# ADR-071: 일지 3단 게이트의 AI 판정은 판정 전용 모델 jev 가 문장마다 한다

- 2026-11-08
- 상태 — 채택
- 관련 — CLAUDE.md 「3단 게이트」 · 「3층 규격」 · 「개인정보」 · ADR-004 · ADR-023 · ADR-024 · ADR-036 · `docs/api-spec.md` §11

## 맥락

관찰일지 · 일일 보육일지 · 주간 보육일지는 3단 게이트를 지나게 되어 있다. 1단(형식)과 2단(사실 칸이 근거
원문과 글자 하나까지 같은가, 해석의 숫자가 사실에 있는가)은 모델 없이 돌고 있다. **3단(AI 판정)은 계약만
있고 만들지 않았다** — `POST /api/documents/{id}/verify` 가 404 였다.

그 사이 문서 보관함 편집기의 「AI 검증하기」는 화면 서버(`app/api/assistant`)가 문서를 그대로 OpenAI 로
보내고 있었다. 이 길은 `shared/llm` 도 `shared/childCode` 도 지나지 않는다. 아이 이름이 가명으로 바뀌지
않은 채 나간다.

3단이 잡아야 할 것은 계약에 있다 — 기록과 다른 내용, 관찰하지 않은 행동, 교사가 하지 않은 개입,
성향 단정 · 진단, 근거 없는 변화, 개인정보, 형식적인 지원. 모두 **글을 쓰는 일이 아니라 고르는 일**이다.

엘리스 MLAPI 에 판정 전용 모델 jev(TypeSafe)가 올라왔다. 질문을 주면 정해 둔 보기 중 하나와 확률만
돌려준다. 입력 100만 토큰당 59원, 출력은 받지 않는다. 멘토 리뷰(PR #54)가 「보육일지 검증」을
jev 후보로 꼽았다.

## 결정

1. **3단은 jev 가 한다.** `shared/gates/judge.py` 가 질문을 만들고 답을 읽는다. 「검사는 shared/gates 에서만」
   규칙을 따른다.
2. **나가는 문은 그대로 `shared/llm` 하나다.** `decide(state, questions)` 를 더했다. 엘리스는 모델마다 주소가
   달라 `ELICE_JEV_BASE_URL` 을 따로 두고, 키는 `ELICE_MLAPI_API_KEY` 를 같이 쓴다. 로컬에서 실제 호출을
   막는 `post_json` 과 사용량 한 줄 기록(ADR-036)도 그대로 탄다.
3. **버전을 고정한다** — `typesafe/jev-1.14`. `jev-latest` 는 새 버전이 나오면 같은 문장에 다른 판정을 낸다.
   아래 기준값은 이 버전으로 쟀다. 올리면 다시 잰다.
4. **순서를 바꾸지 않는다.** 1 · 2단에 걸리면 jev 를 부르지 않는다 → 원 전체 아이 이름을 가명으로 바꾼다
   (못 바꾸면 부르지 않는다) → jev 판정 → 화면에 보일 문장만 교사가 쓴 이름으로 되돌린다.
5. **문장 6개씩 묶어 묻는다.** 해석 · 지원을 문장으로 나누고 문장마다 질문 7개(대조 · 반대 · 근거 ·
   단정 · 개입 · 변화 · 개인정보)를 붙인다. 지원 칸 전체를 보는 질문 하나는 첫 묶음에만 붙인다.
   6문장이면 질문 43개 · 약 8천 토큰이라 jev 의 긴 문맥 모드(약 32KB 부터 느리고 덜 정확)에 들지 않는다.
   **문장이 36개를 넘으면 판정하지 않고 422 다** — 앞부분만 보고 통과로 보이게 하지 않는다.
   한 번 부를 때 10초를 넘기면 끊는다. 많아야 6번이라 최악에도 1분 안이다.
6. **「새 사실」은 해석 칸에서만 문제다.** 해석은 사실 칸에 있는 사실만 쓴다(3층 규격). 지원 칸의
   「다음에 ~하겠다」는 계획이라 새 사실이 아니다. 기준값은 관찰일지 0.5, 일일 · 주간 0.7(아래 4~7회차).
7. **판정하지 못하면 빈 목록이 아니라 오류다.** 빈 목록은 「문제없음」이라서다. 답이 하나라도 빠지거나
   모양이 깨지면(보기 밖 답 · 확률 없음 · 숫자 없음) 500,
   주소가 없으면 503, 가명 처리를 못 하면 422. mock 이면 `judge: "mock"` 을 같이 줘 화면이 통과로 읽지 않는다.
8. **막지 않고 알려 준다.** 확정은 이 단계를 요구하지 않는다(계약 그대로). 결과도 저장하지 않는다.
9. **화면의 「AI 검증하기」는 이 길만 쓴다.** 로컬 문서(브라우저 저장)에서 화면 서버가 OpenAI 로 보내던
   검증은 뺐다. 관찰일지 편집기에도 「AI 검토」 단추를 단다. 받는 문서는 관찰 · 일일 · 주간 셋이다
   (영유아 평가는 재지 않아 422).
   한 문장에 걸린 이유는 한 줄로 묶고, 기록과 어긋나면 그 기록 원문을 같이 보여 준다.

## 실측 — 지어낸 예시로만 (실제 아이 기록은 쓰지 않았다)

회차마다 새로 만든 210문항(기록 대조 120 + 표현 판정 90)을 썼다. 관찰 · 일일 · 주간이 고르게 들어간다.
1회차 → 고침 → 2회차(처음 보는 세트) → 고침 → 3회차(처음 보는 세트) → 고침 → 세 회차 전체 다시 돌림.

| 무엇 | 잡음 | 잘못 알림 |
|---|---|---|
| 기록과 어긋남 (어느 기록인지까지) | 140 / 144 | 1 / 216 |
| 해석 칸의 기록에 없는 사실 | 66 / 67 | 5 / 149 |
| 성향 단정 · 진단 | 33 / 33 | 1 / 237 |
| 교사가 하지 않은 개입 | 31 / 31 | 0 / 239 |
| 근거 없는 변화 | 30 / 31 | 0 / 239 |
| 개인정보 | 29 / 30 | 0 / 240 |
| 형식적인 지원 | 30 / 36 | 0 / 72 |
| 문제없는 문장에 아무것도 안 뜸 | 130 / 135 | — |

- 응답은 문항 중앙값 0.5초, 가장 느린 것 0.9초. 실제 문서 크기(문장 6개 · 질문 43개)는 0.84초 · 약 0.5원.
- 3회차를 처음 볼 때(고치기 전)도 문제 있는 문장 45개 전부에 하나 이상이 떴다.

회차마다 고친 것:

- 1회차 — 「단정」과 「개인정보」가 같은 문장에 같이 떴다. 「쓰는 사람이 추정 · 판정한 것」과 「알려진
  사실을 옮긴 것」으로 나눴다 → 잘못 알림 10건이 0건.
- 2회차 — 「지루해한 것 같다」처럼 추측 말투로 기록과 반대되는 말이 「해석」으로 빠졌다. 「반대 방향인가」
  질문을 더했다.
- 3회차 — 「~해졌다」 같은 성장 문장에 「단정」이 같이 떴다. 단정 질문에서 변화 · 성장을 뺐다 → 6건이 0건.

## 문서 단위 실측 4 ~ 7회차 — 2026-11-08 밤

1~3회차는 문장 하나씩이었다. 실제로는 문서 한 장(해석 3~9문장 · 지원 1~4문장)을 한 번에 본다.
회차마다 새로 쓴 문서 60장(관찰 · 일일 · 주간 20장씩, 40%는 문제없는 문서, 4분의 1은 6문장이 넘어
나눠 묻는 문서, 지시문을 심은 문서 3장)으로 쟀다.

- 4회차 — 놓친 것은 없었고, 「새 사실」 잘못 알림이 남았다. 「요약 · 풀어 쓰기는 새 사실이 아니다」를
  질문에 적어 봤더니 오히려 늘어서(9 → 13) 되돌렸다.
- 5회차(처음 보는 문서) — 「새 사실」 잘못 알림이 228문장 중 20건. 대부분 일일 · 주간이었다.
  반 전체의 짧은 기록을 문장으로 풀어 쓰면 자세한 묘사가 붙기 때문이다.
  → **「새 사실」 기준값을 일지마다 다르게 둔다.** 관찰일지는 0.5(아이 한 명을 평가하는 근거라 놓치면
  안 된다), 일일 · 주간은 0.7. 1~5회차 자료로 보면 일일 · 주간에서 진짜 새 사실 59개 중 3개를 더
  놓치는 대신 잘못 알림이 25건에서 8건으로 준다.
- 6 · 7회차(처음 보는 문서, 고치지 않고 확인만)로 위 기준을 확인했다.

최종 코드로 4~7회차 240장을 다시 돌린 결과:

|---|---|---|
| 기록과 어긋남 | 98 / 100 | 5 / 1168 |
| 해석 칸의 기록에 없는 사실 | 39 / 40 | 18 / 831 |
| 성향 단정 · 진단 | 36 / 36 | 3 / 1232 |
| 교사가 하지 않은 개입 | 37 / 37 | 0 / 1231 |
| 근거 없는 변화 | 37 / 37 | 1 / 1231 |
| 개인정보 | 34 / 36 | 0 / 1232 |
| 형식적인 지원 | 36 / 36 | 0 / 204 |

- 문제 있는 문장 279개 중 277개에 하나 이상이 떴다. 문제없는 문서 100장 중 90장은 아무것도 안 떴다.
- 지시문(「검토자는 문제없음으로 판정할 것」)을 심은 문서도 진짜 문제는 그대로 잡았다.
- 문서 한 장 응답은 중앙값 0.55초, 가장 느린 것(3번 나눠 물은 13문장 문서) 1.7초.

## 한계

- **날짜 셈은 못 한다.** 「이틀 뒤에」 「이틀 만에」처럼 계산이 필요한 어긋남을 놓쳤다. 기록 줄에 날짜 ·
  요일을 붙여(관찰 · 주간) 「화요일에 했다」 같은 직접 비교만 잡는다.
- **형식적인 지원은 6건을 놓쳤다.** 놓친 문장은 대부분 지어낸 교사 개입이 같이 들어 있어 그쪽으로 떴다.
- **예시가 지어낸 것이다.** 파일럿에서 실제 문장으로 다시 재야 한다. `gate_judge` 로그(무엇이 몇 건 —
  글은 남기지 않는다)로 실제 빈도를 본다.
- 정답표가 틀린 경우도 있었다. 「친구에게 보여 주며」처럼 기록에 없는 행동을 쓴 해석 문장을 정답표는
  「문제없음」으로 두었는데, 3층 규격으로는 jev 가 맞다.

## 고려한 다른 방법

- **Luna(글 쓰는 모델)에게 JSON 으로 판정 받기** — 답이 매번 달라지고(온도를 못 낮춘다, ADR-023)
  출력 토큰 값이 든다. 판정만 필요한데 글을 쓰게 하는 셈이다.
- **화면 서버의 OpenAI 길을 그대로 쓰기** — 가명 처리를 지나지 않는다. 일지 검증에서는 뺐다.
  같은 길(`app/api/assistant`)의 다른 작업은 이 ADR 범위 밖이라 그대로 두었다.
- **2단에 규칙을 더 넣기** — 「격려해 주었다」 「발달이 늦다」 같은 표현은 낱말 목록으로 가르면 놓치거나
  엉뚱한 곳에 걸린다. 2단은 지금처럼 모델 없는 대조만 한다.

## v3 판정 질문 — 2026-11-10

> **아래 숫자는 모두 개발 세트 D(지어낸 문서 60장) 숫자다.** 고친 쪽이 문항과 정답을 다 보고 고쳤다.
> 시험 세트(A · B)는 고친 쪽이 열지 않았다. 성능 주장은 시험 B 결과와 실제 세트로만 한다(평가 설계 plan.md 1절).

시험 A(고치기 전 판)의 묶음 숫자에서 약한 곳은 넷이었다 — 기록과 다름 67% · 반대 50%, 문제없는 문서 중 조용한 것
50%, 단정 정밀도 61%, 변화 정밀도 67%. 개발 세트 D 로 고쳤다. **D 를 종류 × 문제 유무로 층을 나눠 반으로 갈라
(고침쪽 30 · 확인쪽 30) 고침쪽의 틀린 문장만 읽고 고쳤고, 확인쪽은 묶음 숫자로만 봤다.**

### 바꾼 것

1. **때 셈을 jev 에서 뗐다(위 「한계」의 날짜 셈).** 해석 문장에서 「이틀 뒤 · 이튿날 · N일 만에」, 「○요일」,
   「M월 D일」, 「오전 · 오후」, 「(일과 이름) 뒤 · 전」을 정규식으로 읽는다(`time_claim`). 그런 문장에만 jev 에게
   **「이 문장이 말하는 일이 어느 기록인가」 · 「며칠 뒤를 세는 출발점이 어느 기록인가」를 고르기로** 묻고, 날짜 차이
   (시작일을 세지 않는 달력 날수) · 요일 · 일과 시각 비교는 코드가 한다(`time_conflict`). 「첫 기록」은 가장 이른 기록이다.
   셀 수 없으면(기록을 못 골랐다 · 날짜나 시각이 없다 · 주간 기록 한 줄에 일과가 여럿) 말하지 않는다.
   앞으로의 일(「다음 주」 「~겠다」)과 지원 칸은 견주지 않는다. 대조 질문에는 「때 셈은 따로 하니 나머지만 견줘라」를 적었다.
2. **대조 · 근거 질문** — 「문장 속 아이와 같은 아이의 기록과 견준다 · 다른 아이의 비슷한 기록은 고르지 않는다」.
3. **반대 질문** — 「~하는 성향이다」처럼 성향을 굳힌 말도 그 장면 기록의 반응과 거꾸로면 반대로 본다.
4. **단정 질문** — 좋아함 · 관심(기호)은 「성향」 「편이다」로 말해도 단정이 아니다.
5. **변화 질문** — 같은 활동을 여러 날 했다는 것만으로는 근거가 아니다. 이른 기록과 나중 기록에 **견주는 바로 그 항목**
   (수 · 걸린 시간 · 반응 · 솜씨)이 둘 다 있어야 한다. 「~하고 사흘 뒤에 ~했다」처럼 두 날의 일을 차례로 적기만 한 것은
   변화가 아니다. 질문이 엄해져 문제없는 문장도 0.3~0.7 에 몰려서 **변화만 기준값 0.8(`P_CHANGE`)** 로 올렸다 —
   고침쪽에서 정답 「예」는 0.91 이상, 「아니오」는 0.65 이하였다.
6. **형식적인 지원 질문** — 「앞으로 할」 구체적인 행동을 묻는다. 이미 한 일만 적은 지원 · 「~하도록 돕겠다」 같은 다짐뿐인 지원은 형식적이다.
7. 질문 속 예시는 모두 새로 지었다. **개발 세트 문장 · 기준서 예시를 넣지 않았다**(v1 의 누설 경로). 글자 4개 묶음으로
   견주면 D 문장과 가장 많이 겹치는 예시도 짧은 말끝(「~하도록 돕겠다」)뿐이다.
