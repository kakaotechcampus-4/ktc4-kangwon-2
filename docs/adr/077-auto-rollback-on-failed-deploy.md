# ADR-077: 교체 뒤 서버 안에서 서비스가 안 살아나면 같은 배포 run 이 직전 성공 버전으로 되돌린다

- 날짜: 2026-11-09
- 상태: 제안 — 구현됨(PR #452), 운영 연습 전. 연습(`docs/evaluation/09-deployment.md` 「더 모을 근거」)을 마치면 채택으로 바꾼다
- 번호: 처음에 075 로 잡았는데 #459(LLM 재시도)가 075 로 먼저 머지됐고 076 은 #455 가 쓰고 있어 077 로 옮겼다. #452 의 앞 커밋 메시지에 남은 「ADR-075」는 이 ADR 이다

## 맥락

[실측] 배포 뒤 확인(`.github/workflows/deploy.yml` 「Health check」, `/health/ready` 30번)이 실패하면 run 이 실패하고
Discord 알림만 간다. 직전 버전으로 돌아가지 않는다 — 사람이 알림을 보고 손 롤백(`ref` 에 SHA)을 해야 한다.

[실측] 그 확인은 GitHub 러너가 인터넷을 건너 도메인으로 묻는다. 2026-10-11 배포는 서버가 멀쩡했는데 secret 에 남은 옛 IP 때문에
확인만 실패했다(`docs/evaluation/09-deployment.md` 「배포 사고 하나를 끝까지 추적했다」). 밖에서 본 실패로 되감으면
멀쩡한 새 버전을 옛 코드로 내린다 — 옛 코드는 새 코드가 쓴 JSONB 키를 저장할 때 버린다(같은 문서 「운영에서 롤백을 한 번 해 봤다」).

[실측] `scripts/deploy.sh` 는 `docker compose up -d` 와 nginx reload 뒤에 서비스가 떴는지 보지 않고 「배포 끝」을 찍는다.
실패한 명령의 종료 코드는 `set -e` 로 죽은 명령의 것이 그대로 나와, 코드 숫자만으로는 「교체까지 했는데 안 살아났다」를 다른 실패와 가를 수 없었다.

## 결정

교체 뒤 **서버 안에서** 서비스가 안 살아난 것만 전용 종료 코드로 알리고, 그 코드에서만 같은 run 안에서 되돌린다.

1. **판정은 서버 안에서.** `deploy.sh` 의 `wait_ready` 가 `up -d` · nginx reload 뒤, `docker image prune` **전**에 서버 자신의 nginx 에
   `http://127.0.0.1/health/ready`(backend · DB)와 `http://127.0.0.1/`(frontend 화면)를 묻는다. 둘 다 200 이고 curl 도 종료 0 이어야 통과다.
   2초 간격 30번(빠른 실패는 약 60초). 끝내 안 되면 마지막 코드 둘을 찍고 **종료 코드 3**으로 끝나며 prune 은 하지 않는다.
2. **3 은 그 하나의 뜻이다.** `set -Eeuo pipefail` 에 `trap 'exit 1' ERR` 를 더해 예상 밖 실패는 전부 1 이다(docker 나 git 이 3 으로 죽어도 롤백이 돌지 않는다).
   root → ubuntu 재실행 구간도 자식의 코드를 그대로 낸다.
3. **서버 잠금.** ubuntu 로 도는 쪽에서 `flock` 으로 `/tmp/ssuksak-deploy.lock` 을 잡고 최대 1500초 기다린다. 워크플로 `concurrency` 는
   러너 쪽만 막아서, 손 배포(Session Manager)와 자동 배포가 서버에서 겹치는 것은 이 잠금이 막는다.
4. **보내기 · 기다리기는 `scripts/ssm-deploy.sh` 로 옮긴다.** 같은 스크립트를 배포와 롤백이 둘 다 부른다. 종료 코드는 서버의 것을 그대로 낸다 —
   성공 0 · 실패는 서버 코드(1~255) · 기다린 시간 안에 안 끝남 124 · 취소 · 시간 초과 125 · 그 밖(보내기 · 읽기 · 해석 실패) 1. 이 스크립트가 3 을 만들어 내는 일은 없다.
5. **3 일 때만 같은 run 안에서 되돌린다.** push 배포는 늘, 손 배포는 `auto_rollback` 을 켰을 때만. 대상 L 은 **마지막으로 성공한 배포 run 이 올린 커밋**이다 —
   `gh run list --workflow deploy.yml --status success --limit 1` 의 run 로그에서 `올릴 커밋 <40자리 SHA>` 줄을 읽는다(브랜치 · 이벤트를 안 가린다).
   L 이 없거나 방금 올린 F 와 같으면 되돌리지 않는다. 되돌리기는 같은 `deploy.sh` 에 SHA 를 넘기는 평소 롤백 길이다 — 마이그레이션을 건너는 판정(ADR-073)도 그대로 받는다.
6. **되돌려도 run 은 실패다.** 초록으로 끝나면 다음 롤백이 「마지막 성공」으로 방금 실패한 F 를 고른다.
7. **밖에서 확인은 알림만.** 「Health check」는 배포가 성공했거나 롤백이 성공한 뒤에만 돌고, 실패해도 되돌리지 않는다. DNS · 인증서 · secret 문제는 코드를 되감아도 안 고쳐진다.
8. **알림은 한 스텝에서 갈래를 낸다.** 롤백 성공(🟠, push 면 「브랜치 끝은 아직 그대로다 — 되돌리는 PR 이 필요하다」) ·
   3 인데 되돌리지 못함(🔴, 이유: 롤백 코드 · 대상 없음 · 손 배포라 꺼짐) · 124/125(서버 직접 확인) · 그 밖의 실패 · 서버 안은 정상인데 밖에서만 안 닿음 ·
   되돌렸는데 밖에서 안 닿음.

## 근거

- [실측] 2026-11-09 운영 서버에서 읽기 전용(SSM)으로 확인했다. 서버 안에서 `curl http://127.0.0.1/health/ready` 와 `http://127.0.0.1/` 가 둘 다 200, 약 0.004초다.
  nginx 로그의 출발지는 `172.28.0.1` 이다 — `nginx/nginx.conf` 의 localhost 블록이 받는다(`allow 172.28.0.1`). `localhost` 는 `::1` 로 붙어서 구현은 `127.0.0.1` 로 IPv4 를 고정한다.
- [실측] 10-11 의 옛 IP 사례(맥락)가 밖에서 본 실패로 판정하면 안 되는 이유다. 서버 안 판정은 DNS · 인증서 · IP 가 끼지 않는다.
- [실측] 대상 찾기를 실제 기록으로 손 시험했다(2026-11-09, 읽기 전용 `gh`). 마지막 성공 run `42505477177` 의 로그에서 `cdb48cd5…`(PR #448 머지, 그때 develop 끝)가 나왔다.
  손 배포 run `42264552753`(11-07 롤백 연습)은 `run.sha` 가 `8d4630a8` 인데 로그의 「올릴 커밋」은 `d59ceaf8` 로, **실제로 올라간 것**이다. 그래서 `run.sha` 가 아니라 로그를 읽는다.
  SHA 고정 이전(11-04 전) run 은 그 줄이 없어 대상을 못 찾고 되돌리지 않는다.
- [실측] ERR 트랩은 `set +e` 로 감싼 구간에서도 외부 명령 실패에 걸려 종료 코드를 1 로 만든다. 맥의 bash 3.2 에서 시험했고, 서버(bash 5)에서는 CI 와 운영 연습이 확인한다.
  그래서 root → ubuntu 래퍼를 `|| status=$?` 꼴로 바꿨고, 가짜 `runuser` 로 root 에서 시작해 3 이 그대로 나오는지 테스트가 본다(`backend/tests/test_deploy_script.py`).
  `$(…)` 안에서 죽은 명령의 코드도 1 로 바뀐다 — 처음 구현은 curl 종료 코드 28 이 1 로 찍혔고 테스트가 잡았다. 그래서 `probe` 는 안에서 `||` 로 코드를 받는다.
  `revision_file` 도 같은 꼴이었다: git grep 이 깨진 코드(128)가 1(못 찾음)로 뭉개져 「마이그레이션 폴더를 읽지 못했다」 거절이 develop 쪽 이유로 새 나갔다(ADR-073 판정이 틀어진다).
  안쪽에 `|| exit "$?"` 를 둬서 고쳤고, 거절 이유 글까지 테스트가 본다.
- [실측] 테스트가 3 의 두 경로를 본다 — 안 살아남(ready 503 · 화면 502 · 200 인데 curl 이 도중에 죽음)은 3, 그 밖의 실패(가짜 build 가 3 으로 죽음 · DB 리비전 못 읽음)는 1.
  `ssm-deploy.sh` 는 가짜 `aws` 로 상태별 종료 코드와 보내는 `commands` 의 첫 줄이 쉬뱅인지를 본다(`backend/tests/test_ssm_deploy_script.py`).
- [판단] 3 이 아닌 실패는 되돌리지 않는다. 124 · 125 는 서버가 어떤 상태인지 모른다. 1 은 일반 실패라 컨테이너를 바꿨는지도 서비스가 어떤 상태인지도 보장하지 않는다 —
  판정 거절 · 빌드 실패는 교체 전에 멈추지만, `up -d` 실패 · nginx reload 와 restart 가 둘 다 실패 · 서비스가 살아난 뒤의 prune 실패도 1 이다(가짜 서버로 재현했다).
  그래서 사람이 서버를 본다.
- [판단] 대상을 develop 으로 좁히지 않고 「마지막으로 성공한 배포」로 잡았다. 서버는 main 이든 develop 이든 손으로 올린 커밋이든 올려 둘 수 있어서, 브랜치로 좁히면 실제 직전 버전을 건너뛴다.
- [판단] 2초 × 30번(약 60초)은 11-07 롤백 연습에서 `up -d` 가 backend · frontend 를 바꾸는 동안의 끊김이 약 5초였던 것에 비해 12배 여유다.
- [판단] 설계안은 opus 검토(고쳐서 진행)와 Codex 플랜 검사(10건 반영)를 거쳤다. 「판정을 서버 안에서」와 「같은 run 안에서 되돌린다」는 그 검토 뒤에 정한 방향이다.

## 대안

- **알림만 둔다(최소안)** — 지금 그대로다. 사람이 알림을 보고 직전 SHA 를 찾아 손 롤백한다. 사람이 없는 시간에는 장애가 길어진다.
- **밖에서 확인(Health check)이 실패하면 되돌린다** — 10-11 의 옛 IP 처럼 서버가 멀쩡한데 새 버전을 내린다. DNS · 인증서 · secret 이 원인이면 되감아도 안 고쳐진다.
- **롤백을 새 `workflow_dispatch` 로 자기 호출한다** — `actions: write` 권한이 필요하고(지금은 읽기만 늘렸다), 같은 `concurrency` 그룹이라 새 run 은 현재 run 이 끝나야 시작한다.
  서버가 죽은 채 기다린다.
- **대상을 develop 에서 마지막으로 성공한 배포로 좁힌다** — 위 [판단]. main 배포나 손 배포로 올라간 버전을 건너뛴다.
- **DB 를 자동으로 내린다** — ADR-073 과 같은 이유로 안 한다. 데이터가 지워질 수 있다.

## 결과

- `deploy.sh` 는 교체 뒤 서버 안 확인을 통과해야 prune 하고 「배포 끝」을 찍는다. 안 살아나면 종료 코드 3 이고, 정상 배포에는 첫 시도에 통과하는 몇 초가 더 든다.
- `deploy.sh` 의 종료 코드에 뜻이 생겼다 — 3 만 롤백 신호이고 나머지 실패는 1. 서버에는 잠금이 생겨 겹친 배포가 기다린다.
- `deploy.yml` 의 스텝이 「배포(코드를 output 으로)→ 자동 롤백 → Health check → 배포 판정 → 알림」으로 바뀐다. `actions: read` 만 더했고 쓰기 권한은 안 늘렸다.
  손 배포에 입력 `auto_rollback` 이 생긴다(기본 꺼짐).
- 자동 롤백이 돌면 서버는 L 로 돌지만 run 은 실패로 남는다. develop 끝은 그대로라 **되돌리는 PR 이 필요하다** — 안 하면 다음 머지가 같은 실패를 되풀이할 수 있다.
- 이 ADR 의 PR 은 GitHub 설정을 바꾸지 않는다.

## 한계

- **응답 코드만 본다.** 화면이 뜨지만 내용이 깨진 경우, 기능 버그(ready 200 이면 안 걸린다)는 못 잡는다. 인증서 · DNS · IP 문제는 알림만 간다.
- **시작이 기다림보다 느리면 멀쩡한 판도 되돌려진다.** 2초 × 30번(빠른 502 · 503 이 오면 약 60초) 안에 둘 다 200 이 안 되면 3 이다 —
  예컨대 frontend 가 61초 뒤에 200 이 되는 판. 손잡이는 `deploy.sh` 의 `READY_TRIES` · `READY_INTERVAL` 이다. 지금은 30 × 2초로 둔다.
- **`/` 가 인증 없이 200 을 준다는 가정이다**(2026-11-09 운영에서 200 확인). 화면이 로그인 쪽으로 3xx 를 내게 바뀌면 모든 배포가 3 으로 끝나 자동 롤백이 돈다.
  그때는 확인 주소(`wait_ready` 의 `/`)를 고친다.
- **실패한 컨테이너 로그가 되감기(컨테이너 재생성)로 사라진다.** journald 로 남기는 설정(ADR-058)이 켜져 있어야 남는다.
- **실패의 원인이 배포 스크립트 자체면 롤백도 같은 스크립트로 실패한다.** 이때는 알림만 가고 사람이 본다.
- **마이그레이션 판정(ADR-073)이 거절하면 사람이 한다.** 특히 직전 성공이 main 배포였던 경우 — ADR-073 이 건너뛰게 하는 것은 develop 이력에서 DB 리비전을 들여온 PR 의 머지 직전 커밋 하나뿐이다.
- **롤백 뒤에도 develop 끝은 그대로다.** 되돌리는 PR 없이 다음 머지가 들어오면 같은 실패가 다시 난다.
- **「마지막 성공」은 서버 안 · 밖 확인을 둘 다 통과한 run 이다.** 밖 확인에서만 실패한 run 은 서버에서 실제로 돌던 버전인데도 L 이 되지 못해, 실제로 돌던 버전보다 앞 버전으로 갈 수 있다.
- **`production` environment 에 보호 규칙(승인자)을 켜면 이 설계를 다시 본다.** 롤백이 같은 job 안에서 돌아 별도 승인 없이 서버를 바꾼다.
- **롤백 스텝 · 알림 갈래는 단위 테스트가 없다.** 워크플로 안의 셸이라서다. 대상 찾기는 위 실제 기록으로, 갈래는 가짜 `gh` · `curl` 로 한 번씩 손으로 돌려 봤고(저장소에 넣지 않았다), 나머지는 운영 연습이 본다.
- **운영 연습 전이다.** 머지 배포가 성공해 L 이 생긴 뒤, L 위에서 `/health/ready` 만 503 을 내는 커밋 F 를 `auto_rollback=true` 로 손 배포해 3 → 같은 run 안 롤백 → 서버 안 · 밖 ready 200 → 알림까지 본다.
- **flock 은 서버에 `flock`(util-linux)이 있어야 한다.** 우분투 기본이다. 없으면 배포가 멈춘다.
