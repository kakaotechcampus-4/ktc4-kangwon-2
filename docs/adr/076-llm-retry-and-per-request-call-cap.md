# ADR-076: LLM 일시 오류는 한 번 더 부르고, 생성 요청 하나의 호출 수에 상한을 둔다

- 날짜: 2026-11-09
- 상태: 제안 — 구현 중(draft PR #455). 머지 뒤 채택으로 바꾼다

## 맥락

[실측] `backend/app/shared/llm/client.py` 는 호출이 한 번 실패하면 그대로 끝났다. 다시 부르지 않았다.

- 제한 시간 30초(`TIMEOUT_SECONDS`)
- 401 · 403 · 429 는 `LlmBudgetExceeded`(계약 `LLM_BUDGET_EXCEEDED` 503, 화면은 「운영 문의」), 그 밖 HTTP 오류는 `LlmFailed`
- 연결 실패 · 시간 초과 · 깨진 JSON 도 `LlmFailed`(계약 `GENERATION_FAILED` 500)

그래서 엘리스 쪽이 몇 초 흔들리면 교사는 생성 실패를 보고 처음부터 다시 누른다.

[실측] 이건 일부러 그렇게 둔 것이었다. `docs/evaluation/05-agentic-implementation.md` 「실패했을 때」(2026-11-04 정리)는
「같은 요청을 몰래 다시 보내지 않는다 — 같은 비용이 두 번 나가고, 교사는 기다리는 줄 모른다」였다. 이 ADR 이 그 줄을 바꾼다.

[실측] 스트림이 아닌 호출은 모두 `post_json` 하나를 지난다 — 연간 주제형 · 주간(스트림이 아닐 때) · 문서 초안 · 연간 가져오기 추출 ·
칸 재생성 · jev 판정(`decide`). 여기 두면 이 길들이 함께 버틴다. 월간(주제형 · 놀이)과 놀이형 연간은 스트림(`post_stream`)이라 재시도 밖이다.

[실측] 생성 요청 하나가 LLM 을 몇 번 부르는지는 `ssuksak.timing` 의 run 이 이미 센다(`run.llm_calls`). 상한은 없었다.
재시도를 넣으면 호출 수가 늘 수 있어서 상한을 같이 둔다.

## 결정

1. **`post_json` 안에서 한 번만 더 부른다.** 다시 부르는 실패:
   ```
   연결 실패(연결 거부 · DNS · 연결 시간 초과) · 응답 대기 시간 초과
   502 · 503 · 504
   429  — 단 본문에 insufficient_quota 가 있거나 Retry-After 가 5초를 넘으면 다시 부르지 않는다
   ```
   다시 부르지 않는 것: 401 · 403 · 그 밖 4xx · 500 · 깨진 JSON · 스트림(`post_stream`, 일부를 읽은 뒤라 다시 못 부른다).
   쉬는 시간은 1초, 429 의 `Retry-After` 가 5초 이하면 그 값이다.
2. **끝내 실패하면 분류는 그대로다.** 401 · 403 · 429 → `LLM_BUDGET_EXCEEDED`, 나머지 → `GENERATION_FAILED`. API 계약은 바뀌지 않는다.
3. **생성 요청 하나(timing run) 안에서 LLM 호출은 6번까지다.** 7번째는 부르지 않고 `GENERATION_FAILED` 로 끝난다.
   스트림도 같은 상한에 걸린다. run 이 없는 호출(문서 초안 · 칸 재생성 · 연간 가져오기 추출 · jev 판정)은 상한 밖이다.
4. **시도마다 `llm_call` 한 줄이 남는다**(실패한 시도는 outcome 이 failed · timeout · budget). `llm_usage` 는 지금처럼 성공한 호출만 한 줄이다.

경로별로 설계상 몇 번 부르는지는 아래 「근거」 표에 적는다.

## 근거

- **429 를 일시 한도로 본다.** [판단] 우리 예산을 넘으면 카테캠이 키를 지운다(CLAUDE.md 「LLM 예산」). [출처] 엘리스 문서는 「잘못됐거나 만료된 키는 인증 오류를 낸다」고만 적는다
  (help.elice.io ML API 「API Key 관리하기」 · 「API 요청」, 2026-11-09 확인). 그래서 예산 초과는 401 · 403 으로 올 것이고, 429 는 속도 제한일 가능성이 크다.
  엘리스 문서에는 429 와 오류 본문 형식이 없다. 크레딧 소진을 429 로 줄 때를 대비해 `insufficient_quota` 가 보이면 다시 부르지 않는다.
- **실제 429 는 본 적이 없다.** [실측] 운영 backend 로그는 `json-file` 이라 배포마다 지워지고, journald(ADR-058)는 서버에 아직 적용되지 않았다(#349).
  2026-11-09 SSM 으로 확인 — `scripts/llm-usage.sh` 가 「llm_usage 줄이 없다」, 02:34 KST 에 뜬 컨테이너에는 LLM 호출이 0건이다.
- **시간 초과를 다시 부르면 그 호출이 두 번 과금될 수 있다.** 엘리스가 이미 답을 만들고 있었으면 토큰이 두 번 나간다. [실측] 10/21 주간 실측 토큰
  (`docs/weekly-llm-live-smoke-20261021.md`: 입력 7.8k~10.2k · 출력 0.7k~1.0k)에 지금 단가(`scripts/llm-usage.sh` 의 sol 단가)를 곱하면 문서 한 번이 약 ₩30~45 다.
  실측 분량이면 6번을 다 써도 요청 하나에 ₩270 안팎이다(₩45 × 6). 상한은 호출 수이지 토큰 · 금액이 아니라서, 프롬프트가 커지면 그만큼 는다.
  [사용자 결정 2026-11-09] 엘리스 크레딧이 넉넉하다고 확인해 넓은 쪽을 골랐다.
- **상한은 월 예산 카운터와 다르다.** 70% 경고 · 90% 차단 카운터는 2026-09-21 무효가 됐다 — 파일럿 중 교사 앞에서 서비스가 멈추면 안 되고, 사용량은 담당자가 본다.
  이 상한은 **요청 하나 안에서** 호출이 불어나는 것만 막는다. 월 합계는 세지 않는다.
- **최악 대기가 nginx 안에 들어온다.** 호출 하나가 30 + 1 + 30초(429 에 `Retry-After` 5초면 30 + 5 + 30초)다.
  계획안 경로는 270 · 510초, 그 밖 `/api/` 는 120초다(`nginx/app-routes.conf` · `nginx/nginx.conf`).
  jev 판정만 예외다 — 문서당 6묶음이 모두 시간 초과 뒤 재시도로 살아나면 최대 (10 + 1 + 10) × 6 = 126초라 120초에 먼저 걸려
  화면이 504 를 볼 수 있다. 재시도 전에는 같은 상황이 첫 시간 초과(10초)에 바로 실패였다. 묶음 5개 이하면 120초 안이다.
  [판단] 드문 경우라 받아들인다. 자주 보이면 `/verify` 경로의 nginx 시간을 따로 늘린다.

- **상한 6은 지금 흐름을 막지 않는다.** [실측] 생성 요청 하나(timing run)가 설계상 부르는 횟수(2026-11-09 코드 확인):
  ```
  run kind         post_json   post_stream   재시도까지 최대   근거
  annual_theme     2           0             4               router.py:455 → llm.py:63 · annual_content.py:149
  annual_play      0           4             4               generate_play_project_plan.py:50 · :136 (구간 4개, 수리 없음)
  monthly_theme    0           2             2               planner/service.py:73 · :103 (첫 호출 + 수리 최대 1)
  monthly_play     0           2             2               generate_play_monthly_plan.py:326 · :347
  weekly           2 또는 0    0 또는 2       4               planner/weekly.py:979 · :1011
  ```
  run 을 열지 않아 상한이 걸리지 않는 경로 — 월간 칸 재생성 · 연간 가져오기 추출 · 문서 초안은 `post_json` 한 번(재시도까지 2번),
  주간 칸 재생성은 수리까지 두 번(재시도까지 4번, `weekly_lifecycle.py:334` 가 수리하는 WeeklyPlanner 를 쓴다), jev 는 문서당 6번(재시도까지 12번)이다.

## 대안

- **모델에 닿기 전 실패(연결 실패 · 503)만 다시 부르기** — 과금 위험이 없지만 시간 초과 · 429 를 못 버틴다. 크레딧이 넉넉해 넓은 쪽을 골랐다.
- **`complete_json` 에만 두기** — 월간 Core 어댑터와 jev 판정이 빠진다.
- **LLM 이 끝내 실패하면 규칙만으로 초안 만들기(폴백)** — `GENERATION_FAILED` 계약과 ADR-032 를 바꾸는 일이라 이 ADR 밖이다.

## 결과

- 일시 오류에 교사가 생성 실패를 덜 본다. 실패해도 화면 안내(계약)는 그대로다.
- 다시 부르는 동안 화면은 따로 알리지 않고 그냥 기다린다 — 호출 하나에 많아야 31초 더(429 에 `Retry-After` 5초가 오면 35초). 11/04 의 「교사는 기다리는 줄 모른다」는 이 한도 안에서 받아들인다.
- 실패한 시도도 `llm_call` 로 남아 몇 번 다시 불렀는지 보인다. 단 서버 로그가 남아야 볼 수 있다 — #349 가 먼저다.
- 새 기능이 생성 요청 하나에서 LLM 을 3번 넘게 부르게 되면(재시도까지 6번을 넘을 수 있으면) 이 상한을 같이 고친다.
