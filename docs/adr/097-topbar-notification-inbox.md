# ADR-097: 상단바 알림함 — 열람 요청이 오고 답이 나오면 어느 화면에서나 종으로 본다

- 날짜: 2026-11-11
- 상태: 채택
- 관련: ADR-059(§8 · §10 · §12 를 따르고 보충) · ADR-068(맞승인) · ADR-029(메일 의존 없음) · ADR-007(알림장 스펙아웃) · ADR-073(롤백 한 칸) · ADR-094(운영 반영) · `docs/api-spec.md` §2-2 「알림함」

## 맥락

ADR-059 는 「내 요청 목록」 API 를 두지 않았고(§8), 받은 요청을 화면 안 목록으로만 알리게 했다(§12).
그 결과 두 쪽에 공백이 있다.

- **보낸 쪽은 결과를 볼 곳이 없다.** 요청이 승인 · 거절 · 취소돼도 반 목록의 `my_access` 가 바뀔 뿐, 바뀌었다고 알려 주는 곳이 없다(§8).
- **받은 쪽은 문서 보관함에 들어가야 대기 수가 보인다.** 다른 화면에 있으면 요청이 와 있는지 모른다.

[실측] `class_access/router.py` 의 요청 · 승인 · 거절 · 취소 네 지점이 이 사건의 전부이고, 지금은 어느 것도 기록을 남기지 않는다.

## 결정

1. **화면 안 알림만 둔다.** 표 `notifications`(받는 계정 · 사건 종류 · 열람 요청 줄 · 만든 시각 · 읽은 시각)를 더하고,
   상단바 종이 `GET /api/me/notifications` 로 최근 30개를 읽는다. 메일 · 푸시 · 알림톡으로 내보내지 않는다.
2. **사건은 네 가지가 전부다.**

   | kind | 받는 사람 | 만드는 곳 |
   |---|---|---|
   | `ACCESS_REQUESTED` | 반 주인 | 새 요청 줄 · 거절 / 취소된 줄의 재요청 |
   | `ACCESS_APPROVED` · `ACCESS_REJECTED` · `ACCESS_REVOKED` | 요청자 | 주인의 승인 · 거절 · 승인 취소 |

   맞승인(ADR-068)으로 자동으로 열리는 반대 줄에는 알림을 만들지 않는다.
3. **알림은 그것을 만든 변경과 같은 트랜잭션에 넣는다.** 요청 줄을 쓰고 알림을 더한 뒤 한 번에 커밋한다.
4. **처리된 요청의 「요청이 왔다」는 같이 읽음이 된다.** 승인 · 거절 때, 그리고 맞승인으로 상대의 `PENDING` 이
   `APPROVED` 가 될 때 그 요청의 `ACCESS_REQUESTED` 알림에 `read_at` 을 채운다. 보관함에서 처리했는데 종에 1 이 남는 것을 막는다.
5. **읽음은 `POST /api/me/notifications/read` 로 id 를 보내서 한다.** body 가 필수이고 1~30개다.
   「body 없음 = 전부 읽음」은 두지 않는다. 남의 id · 없는 id 는 조용히 건너뛰고, 이미 읽은 알림의 시각은 덮지 않는다.
6. **알림 줄에 반 이름 · 요청자 이름을 복사해 두지 않는다.** 읽을 때 요청 줄에서 `classes.name` · `users.name` 을 JOIN 한다.
7. **폴링 · 실시간(SSE) · 알림 설정 화면은 없다.** 화면이 다시 받는 때는 화면 쪽에서 정한다.
8. **열람 요청 하나가 낳는 사건만 다룬다.** 생성 실패 · 원장 현황 같은 알림은 이 결정 밖이다.

## 근거

- [판단] 요청은 받은 사람이 봐야 움직인다. 알려 주지 않으면 승인이 늦어지고, 요청한 교사는 결과를 알려고 보관함을 열어 봐야 한다.
- [판단] 반 이름 · 요청자 이름은 요청 줄에서 나온다. [실측] 반 주인(`classes.teacher_id`)을 바꾸는 경로도 반 · 계정 · 요청 줄을 지우는 경로도 코드에 없다(ADR-059 §결과 「담임 바꾸기는 없다」).
  사본을 두면 같은 값이 두 곳에 있게 될 뿐이다.
- [판단] 같은 트랜잭션에 넣어야 「승인은 됐는데 알림이 없다」「알림은 갔는데 승인은 롤백됐다」가 없다.
  CLAUDE.md 의 「부가 기능이 죽어도 본 기능은 돌아간다」는 **트렌드봇 · 외부 API 같은 외부 의존**에 건 규칙이다.
  같은 DB 안의 INSERT 한 줄은 외부 의존이 아니고, 이게 실패하는 때는 우리 코드의 결함뿐이라 조용히 삼키는 것보다 드러나는 것이 낫다.
- [판단] 알림 줄은 사건이 일어날 때 한 번 만들고 지우지 않는다. 읽는 쪽이 30개로 자르므로 표가 커져도 응답은 커지지 않는다.
- [실측] 운영 세션은 `autoflush=False` 다(`app/db.py`). 읽음 처리를 요청의 상태를 하위질의로 보는 UPDATE 로 짜면 테스트(autoflush 켬)와 운영이 다르게 돈다.
  그래서 id 로만 UPDATE 한다.

### 「알림장」(ADR-007)과 다르다

ADR-007 의 알림장은 부모에게 가는 식사 · 배변 · 수면 · 투약 기록이다. 사실기록형이라 AI 가 쓰면 위조이고, 그래서 스펙아웃했다.
이 알림함은 교사 본인 화면에 뜨는 시스템 알림이다. 문서가 아니고, 아동 정보가 없고(반 이름 · 교사 계정 이름뿐), LLM 을 부르지 않는다.
이름이 비슷할 뿐 같은 종류가 아니다.

### 「자동 제출 · 자동 발송 없음」(PRD)과 다르다

그 규칙은 교사의 문서를 교사 모르게 바깥으로 내보내는 것을 막는다. 이 알림은 앱 안에서 교사 계정에만 보이고 바깥으로 나가는 것이 없다.
메일 의존을 만들지 않으므로 ADR-029 도 그대로다.

### ADR-059 와의 관계

- **§8 「내 요청 목록 API 는 따로 두지 않는다」 — 따른다.** 목록 API 는 여전히 없다. 알림함은 요청의 현재 상태가 아니라 사건을 알린다.
- **§12 「받은 요청은 화면 안 목록으로만 알린다」 — 따르고 보충한다.** 알림도 화면 안이다. 받은 요청 칸이 처리하는 곳이고 종은 거기로 데려다 준다.
- **§10 「이력이 필요하면 이벤트 표를 따로 둔다」 — 이 표가 그것이 아니다.** `notifications` 는 읽는 사람에게 알리는 표이지 요청의 상태 이력이 아니다.
  이전 · 이후 상태와 행위자를 남기지 않고, 화면은 30개만 본다. 이력이 필요해지면 그때 따로 둔다.

## 대안

- **메일 · 푸시 · 알림톡.** 외부 발송 의존이 생긴다. ADR-029 가 메일을 버린 이유(「부가 기능이 죽어도 본 기능은 돈다」)가 그대로 걸린다.
- **요청 줄의 `updated_at` 을 비교해 알림을 계산한다.** 읽음을 저장할 곳이 없고, 거절 뒤 재요청처럼 같은 줄이 되돌아가는 사건을 구별하지 못한다(ADR-059 §10).
- **「내 요청 목록」 API.** §8 을 뒤집는다. 사건이 아니라 상태만 보여서 「방금 승인됐다」를 알리지 못한다.
- **`body` 없이 보내면 전부 읽음.** 화면이 id 를 빠뜨리면 아무도 모르게 모든 알림이 읽힌다. 읽을 id 를 늘 명시하게 한다.
- **폴링 · SSE.** 서버 연결을 오래 쥐거나 주기 호출이 늘어난다. 이번 범위에서는 화면이 열리거나 다시 보일 때만 받는다.
- **알림 줄에 반 이름 · 요청자 이름 복사.** 위 근거.

## 결과

- 마이그레이션 `b5dee31c5ce0` 은 새 표 하나를 더하기만 한다(ADR-073 롤백 한 칸). 직전 코드는 이 표를 모른 채 돌고, 알림이 안 만들어질 뿐 열람 요청 · 승인은 그대로 돈다.
- **운영 반영은 develop → main 머지로 한다(ADR-094).** 그 전에는 운영에 이 경로가 없다.
- `class_access` 는 `notifications` 를 `service.py`(`notify` · `mark_request_read`)로만 부른다. 알림 목록은 요청 · 반 · 계정 모델을 JOIN 해서 읽는다 — `class_access` 도 같은 모델을 읽는다.
- **한계 하나: 폴링이 없다.** 한 화면에 오래 머물면 새 알림이 늦게 보이고, 보관함에서 처리한 직후 종의 숫자가 잠깐 남을 수 있다.
- **한계 둘: 30개.** 오래된 알림은 목록에서 빠지고 안 읽은 수에도 들지 않는다. 읽음으로 보낼 수 있는 id 도 30개다(목록이 주는 최대 개수).
- **기존 문제가 그대로 있다: 두 주인이 서로의 요청을 동시에 승인하면 줄 잠금 순서가 엇갈릴 수 있다**(`decide_request` 가 요청 줄을 잠근 뒤 `_mirror` 가 반대 줄을 잠근다).
  이번 변경이 새로 잡는 잠금은 둘이다 — `request_access` 의 요청 줄 `FOR UPDATE`, 그리고 알림 줄 UPDATE(`mark_request_read` 는 `decide_request` · `_mirror` 안에서, 읽음 `POST` 는 단독으로 부른다). 알림 INSERT 의 외래키 검사도 요청 줄 · 계정 줄을 짧게 공유 잠근다.
  코드 순서로 읽으면 요청 줄을 잠그는 경로는 알림 줄을 그 뒤에 잡고, 읽음 `POST` 는 알림 줄만 한 문장으로 잡고 바로 커밋해서 새 순환은 보이지 않는다. 다만 읽어서 내린 판단이다 — 동시 경합은 시험하지 않았고, 같은 계정이 겹치는 id 로 읽음을 동시에 보내는 경우는 따져 보지 않았다.
  맞승인 교착은 이번에 고치지 않는다.
- 시험은 실제 DB 로 돈다 — 요청 · 승인 · 거절 · 취소 · 맞승인 · 읽음과 남의 알림이 안 보이는 것.
