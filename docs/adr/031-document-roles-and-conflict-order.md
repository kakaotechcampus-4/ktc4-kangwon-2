# ADR-031: 문서는 역할 안내표로 찾고, 서로 다르면 ADR > api-spec > 요구사항 > screen-spec 순으로 따른다

- 2026-10-19
- 상태 — 채택 (PM-01 A, ADR-030)

## 맥락

「문서끼리 다르면 무엇을 따르나」가 정해져 있지 않았다.

- 루트 `CLAUDE.md` 는 「찾는 것 → 문서」 역할 안내표만 있고 서열이 없다.
- 루트는 「`p0-planning/CLAUDE.md` 가 이 파일보다 우선한다」, `p0-planning/CLAUDE.md` 는 「루트를 먼저 읽어라」라고 적었다.
  방향이 엇갈려 보였다.
- 개인 P0 문서에는 서로 다른 우선순위 사슬이 세 개 있었고, 그 사슬이 가리키는 문서 대부분이 팀 저장소에 없었다.
- 이름이 같은 다른 문서가 있었다(개인 `docs/screen-spec.md` 와 팀 `docs/screen-spec.md`).

## 결정

1. **팀 저장소의 역할 안내표(루트 `CLAUDE.md`)가 정본이다.** 무엇이 어디에 있는지는 안내표로 찾는다.
2. **같은 대상을 두 문서가 다르게 적으면 이 순서로 따른다.**

   ```text
   ADR  >  api-spec  >  요구사항명세서  >  screen-spec
   ```

   같은 단계 안에서는 날짜가 늦은 결정이 이긴다. ADR 끼리는 「대체 · 보충」 표시를 따른다.
3. **루트 `CLAUDE.md` 와 `p0-planning/CLAUDE.md` 는 적용 범위가 다르다.** 루트는 팀 전체 규칙, `p0-planning/CLAUDE.md` 는
   `p0-planning/` 안에서만 쓰는 더 좁은 규칙이다. **`p0-planning/` 안에서는 더 좁은 규칙이 우선한다.** 두 파일의 「먼저 읽어라」와
   「우선한다」는 읽는 순서와 적용 범위를 말한 것이라 충돌이 아니다.
4. **저장소 밖 문서는 근거가 아니다.** 개인 P0 문서 · 브랜치에만 있는 문서는 결정을 옮겨 적기 전까지 계약 근거로 인용하지 않는다.
   옮길 때는 원 ID(OD-* · TP-* · D-* · PROV-Y-* · Contract n)를 남긴다(ADR-030 PM-13).
5. **충돌을 찾으면 고치기 전에 적는다.** 어느 문서가 이기는지 위 순서로 분명하지 않으면 임의로 고르지 않고 충돌 위치 · 가능한
   해석 · 영향 · 권장안을 남긴다.

## 근거

- **[출처]** PM-01 = A (2026-10-19, ADR-030). 선택지 A 의 문장 그대로다.
- **[판단]** 서열의 순서는 선택지 A 가 예시로 든 순서다. PM 이 수정 의견 없이 A 를 골라 그대로 적었다(ADR-030 「해석 쟁점」 1).
  - ADR 이 맨 앞인 이유: 결정과 이유가 함께 있고, 대체 · 보충 이력이 남는다.
  - api-spec 이 요구사항보다 앞인 이유: 서버와 화면이 실제로 지키는 약속이고 코드와 테스트가 이 문서를 본다.
  - screen-spec 이 마지막인 이유: 화면 동작은 위 세 문서가 정한 계약 위에 선다.
- **[실측]** 통합 검토의 직접 충돌 12건 대부분이 「어느 문서를 따르나」가 없어서 생겼다(K-24).

## 대안

- **(B) 서열 없이 역할만 적는다.** 겹치면 그때마다 ADR 로 정한다 — 고르지 않았다(PM-01).
- **(C) 개인 문서의 사슬을 팀 문서로 옮긴다.** 그 사슬이 팀 저장소에 없는 문서를 가리킨다 — 고르지 않았다(PM-01).

## 결과

- 루트 `CLAUDE.md` 안내표 아래에 위 서열과 적용 범위를 적는다. `p0-planning/CLAUDE.md` 머리말을 같은 뜻으로 맞춘다.
- 개인 P0 문서의 우선순위 사슬은 팀 규칙이 아니다. 개인 문서 정리는 「이관 → 검증 → 동결 → 승인 후 삭제」 원칙을 따른다(ADR-030).
- `frontend/CLAUDE.md` 가 화면 명세를 PRD 로 가리키던 것을 `docs/screen-spec.md` 로 고친다. 화면 동작의 정본은 screen-spec 이고,
  PRD 는 범위 · 일정 문서다.
