# ADR-044: 놀이 프로젝트형 연간 저장 연결 — 고르기 저장 · 칸 수정 · 확정 · 내려받기 · 이력

- 날짜: 2026-10-27
- 상태 — **제안 (검토 전)** (성진). Core 규칙은 ADR-042 「후속 결정 — 후보 선택 · 편집 · 확정」(2026-10-26 하민)을 따른다.
- 관련 — ADR-042 · ADR-043 · ADR-035 · ADR-039 · api-spec §4~§7-1 · §9 · screen-spec S8

## 맥락

[실측] Core 는 후보 선택 · 칸 편집 · 확정과 이력을 지원한다(`play_project_lifecycle.py`). 서버 · 화면 연결은 아직 없고, ADR-043 §4 는 수정 · 확정 · 이력 · 내보내기를 막으며 §6 은 선택을 화면에만 둔다.
[실측] `plans.revision` 은 이미 있다. 월간 API 는 `expected_revision` 으로 동시 수정을 막는다(api-spec §9-3).
이 문서는 성진의 저장 연결 결정(2026-10-27)을 기록한다. 월간 연결은 범위 밖이다.

## 결정

### 1. 고르기는 즉시 저장하고 네 구간을 모두 보낸다

- 고르기 · ↑ ↓ · 빼기 · 넣기마다 `PUT /api/plans/annual/{id}/selection` 을 보낸다. 본문은 `selections`(네 구간 모두) · `expected_revision` 이다.
- 구간마다 `selected` 는 문서 배치 순서의 `row_key` 배열이다. DRAFT 는 0~5개를 허용한다. 후보 배열 · 값 · 주소 · 이력은 지우거나 다시 정렬하지 않는다.
- 화면은 한 번에 하나만 저장한다. 이전 응답의 revision 으로 다음 요청을 보내고, 기다리는 동안 쌓인 변경은 최신 상태 하나로 합친다. 저장하지 않는다는 안내는 없앤다.
- 전 구간을 먼저 검사하고 한꺼번에 적용한다. 한 구간이라도 틀리면 아무것도 저장하지 않는다. 바뀐 구간마다 `CANDIDATES_SELECTED` 하나를 남긴다. 같은 선택 · 순서면 쓰기 · 이벤트 · revision 증가가 없다.
- [판단] 별도 저장을 잊어도 다시 이어 고를 수 있게 한다. 네 구간 전체를 보내면 화면 상태와 저장 상태를 같은 단위로 비교할 수 있다.

### 2. 칸 글자는 「저장」 버튼으로 저장한다

- 고른 후보의 놀이명 · 지원매체 · 지원 방향만 `PUT /api/plans/annual/{id}/cells/{item_id}` 로 고친다. `item_id` 는 Core ItemId 그대로다. 배움은 누리과정 Reference 원문 표시라 읽기 전용이다.
- 바뀐 칸을 하나씩 저장하며 응답의 revision 을 다음 요청에 넘긴다. 같은 값 편집은 월간(§9-3)처럼 422 `VALIDATION_FAILED` 다.
- 근거 · 생성 방식(`rule_id` · `rule_version` 포함)은 보존하고 `TEACHER_EDITED` 에 이전 값 · 새 값 · 행위자를 남긴다. 선택 해제 뒤 다시 골라도 고친 값이 남는다.
- [판단] 글자를 입력하는 중간값마다 저장하지 않고, 월간과 같은 명시적 저장을 쓴다. 편집 범위와 이력은 하민의 Core 규칙을 따른다(ADR-042 후속).

### 3. 동시 수정은 revision 으로 막는다

- PLAY_PROJECT 생성 · 상세 · 변경 응답에 `revision`(정수 ≥ 1)을 싣는다. 선택 저장 · 칸 편집 · 확정은 `expected_revision` 을 필수로 받는다.
- 서버는 「DRAFT 이고 revision 이 그대로일 때만 쓰고 +1」을 한 문장으로 한다. 실패는 409 `STALE_WRITE` 다. 선택 무변경은 쓰지 않는다.
- 충돌하면 화면은 계획안을 다시 읽고 「다른 곳에서 바뀌었어요. 최신 내용을 다시 불러왔어요.」를 알린다.
- [판단] 행 잠금만으로는 오래된 화면의 덮어쓰기를 알 수 없다. 월간 §9-3 과 같은 계약을 쓴다. 월별 주제형 연간의 기존 행 잠금 · 본문 없는 확정은 바꾸지 않는다.

### 4. 네 구간이 정확히 5개여야 확정한다

- `POST /api/plans/annual/{id}/confirm` 에 `{ "expected_revision": n }` 을 보낸다. 모든 변경의 교사 actor 는 서버가 로그인 계정에서 만든다.
- 부족한 구간이 있으면 422 `VALIDATION_FAILED`, `fields` 는 그 구간 키 배열이다(예: `["m09_m11", "m12_m02"]`). 확정 뒤 선택 · 편집은 409 `ALREADY_CONFIRMED` 다.
- 확정 재호출은 기존 연간 계약대로 200 이고 revision · 최초 확정 시각 · 확정자 · 이력을 바꾸지 않는다. 서버가 Core 를 다시 부르지 않는다.
- 확정은 Core `ConfirmPlayProjectPlan` 을 부르고 **그 결과 본문 전체를 저장한다.** 상태 칸만 바꾸면 계획안 단위 `CONFIRMED` 이벤트가 본문에 없어, 놀이 중심 월간 생성이 부모 확정을 찾지 못해 막힌다(`generate_play_monthly_plan.py` 부모 검사, #240).
- [판단] 화면에서 부족 구간을 바로 알릴 수 있어야 한다. 확정 조건 · actor · 확정 뒤 읽기 전용은 ADR-042 후속, 재호출은 ADR-035 를 따른다.

### 5. 내려받기는 확정본만 연다

- `GET /api/plans/{id}/export/hwp` 는 기본 hwpx, `?format=hwpx|hwp` 를 받는다. DRAFT PLAY_PROJECT 는 409 `GATE_BLOCKED` · 「놀이 프로젝트형 연간계획안은 확정한 뒤 내려받을 수 있습니다.」다.
- 하민의 `backend/app/features/plans/play_project_hwpx.py` 양식 · renderer 에 구간마다 고른 5개만 문서 순서대로 넘긴다. 출처 마커 · 생성 정보는 넣지 않는다.
- [판단] 교사가 확인한 제출 문서만 내려받게 한다. 형식 선택과 서버 안 변환은 ADR-039 를 따른다.

### 6. 변경 이력은 API 만 연다

- `GET /api/plans/annual/{id}/audit` 가 PLAY_PROJECT 의 `CREATED` · `CANDIDATES_SELECTED` · `TEACHER_EDITED` · `CONFIRMED` 를 준다. 선택은 구간별 이전 · 이후 순서, 편집은 칸별 이전 · 이후 값과 행위자 · 시각을 남긴다.
- 화면의 이력 패널은 후속 PR 로 미룬다. 「다른 놀이」도 후속이며 연결 전에는 버튼을 숨긴다.
- [판단] 저장한 행위는 추적하되 이력 화면과 후보 교체까지 이번 연결에 묶지 않는다.

### 7. 연결 PR 은 네 개로 나눈다

- 서버 ① 선택 저장 · 칸 편집 · 응답 `selected` / `revision` / `item_id`, 서버 ② 확정 · 내보내기 · 이력, 화면 ① 저장 연결 · 칸 편집, 화면 ② 확정 · 내려받기 순서다.
- [판단] 저장을 먼저 검토하고 그 위에 확정 · 제출 파일을 붙인다. 서버 · 화면 연결은 성진, Core 는 하민이 맡는다(2026-10-27).

## 근거

- [실측] Core 는 여러 구간을 먼저 검사하고 바뀐 구간만 기록한다. 일부 구간만 받는 것도 허용하므로 **네 구간 필수 검사는 API 몫**이다(`SavePlayProjectSelection`).
- [실측] `find_item` 은 후보의 네 칸을 ItemId 로 찾는다. 편집은 배움 · 미선택 후보 · 빈 값을 거절한다. 같은 값은 Core 가 허용하므로 **같은 값 422 검사는 API 몫**이다(`EditPlayProjectItem` · `PlanItem.edit_by_teacher`).
- [출처] 배움 읽기 전용은 ADR-042 「후속 결정 — 후보 선택 · 편집 · 확정」(2026-10-26 하민)을 따른다 — 배움은 누리과정 원문을 서버가 그리는 칸이고, 허용 ID 를 다시 고르는 기능은 후속이다. 하민 2026-10-27 답(메신저, #223 질문 댓글에 대한 답)으로 다시 확인했다 — `EDITABLE_FIELDS` 에 `learning` 이 없는 것은 누락이 아니고, 내용 ID 다시 고르기는 구현 일정이 없다. 연다면 월간(#251)처럼 현재 연결과 `LinkChange` 를 나누는 방향을 검토하되, 아직 결정이 아니다.
- [실측] Core 의 `selection_incomplete.problems` 는 부족 구간을 담는다. API 는 이를 `fields` 의 구간 키 배열로 옮긴다. renderer 는 네 구간 · 구간당 5개를 요구한다.

## 대안

- 고르기도 버튼으로 저장: 저장을 잊으면 선택 · 순서가 사라진다. 즉시 저장을 택한다.
- 서버 행 잠금만 사용: 요청은 줄 세워도 오래된 화면의 덮어쓰기는 조용히 통과한다.
- 바뀐 구간만 보내기: Core 는 허용하지만 화면 전체 상태를 저장하는 이번 HTTP 계약과 맞지 않는다.
- 초안 내보내기: 교사가 확정하지 않은 문서가 제출되는 길이 생긴다.
- 부족 구간 없이 `fields: []`: 교사가 어느 구간을 채워야 하는지 응답으로 알 수 없다.
- 이력 화면도 지금 연결: 저장 · 확정 · 내려받기와 독립이므로 후속으로 둔다.
- 서버 · 화면을 큰 PR 하나로 연결: 저장과 확정 · 파일을 따로 검토하기 어렵다.

## 결과

- **ADR-043 §4 중 PLAY_PROJECT 수정 · 확정 · 변경 이력 · 내보내기를 모두 409 로 막던 결정과 §6 의 「저장하지 않는다」 및 관련 결과를 대체한다.** 기존 월간 생성 409 는 유지한다. PLAY_MONTHLY Core(#240 · #242 · #243 · #251)는 이번에 연결하지 않는다.
- 응답 · API · S8 을 이 계약으로 맞춘다. 구현은 서버 ① 선택 저장 · 칸 편집 · 응답 확장 → 서버 ② 확정 · 내보내기 · 이력, 화면 ① 저장 · 편집 → 화면 ② 확정 · 내려받기 네 PR 로 나눈다.
- 성진이 서버 · 화면을 연결한다. 하민의 Core 규칙 · 기존 월별 주제형 계약 · 생성 호출 단위는 바꾸지 않는다. 이번 변경은 문서뿐이다.
