# ADR-030: `.hwp` 는 내보낸 hwpx 를 서버 안에서 변환해 만든다 — 기본은 hwpx 다

- 2026-10-19
- 상태 — 채택
- 관련 — ADR-021(결정 3 · 「안 한 것」 대체) · ADR-004(아동 실명) · api-spec §9 · §11 · #154

## 맥락

ADR-021 은 내보내기를 hwpx 로만 하고 `.hwp` 는 만들지 않기로 했다. 근거는 둘이었다 —
`.hwp` 를 **쓰는 도구가 없다**(021 「맥락」 · 「안 한 것」), 시중 변환은 파일을 **남의 서버로 보낸다**(021 결정 3 · 「근거」).
그리고 「파일럿에서 교사가 hwp 아니면 불편하다고 실제로 말하면 그때 다시 본다」(021 「결과」)는 조건을 걸었다.

10주차에 PM 이 hwp 변환을 1순위 결정으로 올렸다(#154). 10/18 조사에서 두 전제가 모두 깨진 것이 나왔고,
10/19 팀이 python-hwpx 로 구현하기로 정했다.

## 결정

1. **`.hwp` 는 우리가 만든 hwpx 를 변환해서 만든다.** `fill_table` · `fill_grid` 가 채운 hwpx 를
   python-hwpx 의 `hwpx.hwp5.writer.write_hwp5` 로 바꾼다. 채우는 코드는 hwpx 한 벌이다.
   변환은 두 내보내기가 같이 쓰는 `shared/hwpx.py` `download()` 한 곳에서 한다.
2. **기본은 hwpx 이고, `.hwp` 는 고른다.** 지금 경로에 쿼리 `?format=hwpx|hwp` 를 더한다.
   `format` 이 없으면 hwpx 다. 다른 값은 422 `VALIDATION_FAILED` 다.
3. **변환이 실패하면 503 `DEPENDENCY_UNAVAILABLE` 로 「hwpx 로 받아주세요」를 준다.**
   `Hwp5Error` 만이 아니라 변환에서 난 예외 전부다. 로그에는 예외 종류만 남긴다.
   변환기를 불러오지 못한 것도 같다 — hwp 를 고를 때만 불러오므로, 깨져도 서버 기동과 hwpx 는 산다
   (트렌드 수집이 `httpx` 를 쓸 때 불러오는 것과 같은 이유다, `trends/collect.py`).
4. **`python-hwpx==6.8.0` 으로 고정한다.**
5. **`.hwp` 의 `Content-Type` 은 `application/x-hwp` 다.**

ADR-021 의 결정 1(hwpx 로 내보냄) · 2(표를 새로 그리지 않음) · 4(확정본만) · 5(출처를 싣지 않음)는 그대로다.
결정 3(변환을 서버에 두지 않음)과 「안 한 것 — `.hwp` 쓰기 · 서버 쪽 변환」을 이 ADR 이 대체한다.

## 근거

- **[실측]** 쓰는 도구가 생겼다. python-hwpx 는 v6.6.0(2026-09-27)부터 HWP 5.0 을 쓴다.
  6.8.0 으로 채운 연간계획안 · 관찰일지 · 일일 보육일지(일과 줄 복제)를 바꾸면 pyhwp(`hwp5html`)가
  다시 읽고 칸 글자가 넣은 값과 같다. 변환은 한 건에 수 ms 다(로컬에서 잼 · 서버에서는 안 쟀다).
- **[실측]** 남의 서버로 보내지 않는다. 변환은 backend 프로세스 안에서 돈다. 설치한 `hwpx` 패키지에
  네트워크 모듈 import 가 없고(`urllib.parse` 문자열 처리뿐) 외부 명령도 부르지 않는다.
- **[실측]** 개인정보 장치가 `.hwp` 로 그대로 넘어간다. 변환기는 `.hwp` 문서 정보를 hwpx 의
  `content.hpf` 에서 가져온다 — 작성자 · 마지막 저장자에 이름을 넣은 양식 사본으로 돌려 보니,
  우리 경로(`_package` 가 비움)를 지난 `.hwp` 는 둘 다 빈칸이었다. 미리보기 글자는 우리가 다시 만든
  `PrvText.txt` 를 UTF-16LE 로 옮긴다.
- **[실측]** Java(hwplib)로도 실물 연간계획안 `.hwp` 를 채울 수 있었다. 그런데 그 결과 파일은 pyhwp 가
  문서 정보를 못 읽는다(hwplib 이 쓰는 `PID_CODEPAGE` 의 `VT_I2` 를 pyhwp 가 지원하지 않는다).
- **[판단]** Java 사이드카는 채우는 코드가 Java 로 한 벌 더, `.hwp` 양식이 따로, 컨테이너 하나와
  배포 스크립트 수정이 붙는다. 그 결과 파일을 우리 양식 등록에 다시 올리면 막힐 것이다(엔드포인트로는 안 돌려 봤다).
- **[실측]** 현장 실물 계획안은 전부 `.hwp` 였다(021 「근거」 첫 항목).
- **[판단]** 교사가 hwp 를 원한다고 **실제로 말한 기록은 아직 없다.** ADR-021 이 「교사가 말하면」을
  조건으로 둔 것은 값이 컸기 때문이다 — 명세 200쪽 · 며칠 · 디버깅 불가 · 개인정보.
  그 값이 변환 몇 줄과 의존성 하나로 줄었고, 현장 양식이 `.hwp` 라 원하는 원 · 교사가 있을 것으로 본다.
- **[판단]** hwpx 를 기본으로 둔다. hwp 쓰기는 3주 된 기능이고 관리자가 한 명이다. 그리고 지금 화면과
  열린 FE 브랜치가 `/export/hwp` 를 불러 hwpx 를 받으므로, 기본을 안 바꾸면 아무것도 깨지지 않는다.
- **[판단]** 실패는 종류를 가리지 않고 503 이다. 변환은 hwpx 를 다 만든 뒤에만 돌아서, 거기서 난 오류는
  무엇이든 「hwp 만 안 되고 hwpx 는 된다」다. 공통 표의 `DEPENDENCY_UNAVAILABLE`(서버가 쓰는 변환기를
  쓸 수 없음 · 재시도해도 같다)과 뜻이 같고, 500 이상이라 서버 로그(`server_error`)에 남아 파일럿 중에 보인다.

## 대안

- **Java(hwplib) 사이드카** — 위 근거. 다시 꺼내면 상시 사이드카로 띄우고, 메모리 상한과
  배포 스크립트(`scripts/deploy.sh` 가 backend · frontend 만 빌드한다)를 먼저 본다.
- **경로를 `/export/hwpx` · `/export/hwp` 로 나누기** — 이름이 정직하다. 대신 지금 `/export/hwp` 의 뜻이
  hwpx 에서 hwp 로 바뀌어 화면 호출을 같은 PR 에서 고쳐야 한다. 안 고치면 지금 버튼이 오류 없이 `.hwp` 를 받는다.
  팀 의견을 받는다.
- **변환이 실패하면 hwpx 를 200 으로 대신 준다** — 교사가 hwp 를 눌렀는데 hwpx 가 온 것을 모를 수 있다.
- **새 에러 코드 422** — 4xx 라 서버 로그에 남지 않는다. 공통 표와 요구사항명세서에 행이 는다.
- **시중 변환 서비스 · 한글 COM(hwpapi)** — 남의 서버로 보낸다 / Windows 와 한글 설치가 필요하다.

## 결과

- 교사는 확정한 연간계획안 · 관찰일지 · 일일 보육일지를 `.hwp` 로도 받을 수 있다.
  화면 버튼은 아직 없다 — 화면은 요청 끝에 `?format=hwp` 를 붙이면 된다.
- **backend 의 lxml 이 7 미만으로 묶인다.** python-hwpx 6.8.0 이 `lxml>=4.9,<7` 을 요구한다.
  지금 lxml 정식판이 6.1.3 이라 당장은 바뀌는 것이 없다. lxml 7 이 나와도 python-hwpx 를 올리기 전까지 6.x 다.
- **python-hwpx 를 올리거나 양식을 바꾸면 세 양식을 `.hwp` 로도 바꿔 한글에서 연다.**
  자동 테스트는 pyhwp 로 다시 읽히는지까지만 본다. 한글 화면 · 칸 안 줄바꿈 · 쪽 넘김은 사람이 본다.
- 미리보기 그림(`PrvImage`)은 양식의 것이 `.hwp` 에도 그대로 들어간다 — 양식 파일은 빈 양식이어야 한다(§11).
- 문서 정보의 날짜는 양식의 값이 그대로 나간다. 연간은 비어 있어 `.hwp` 에서 1601-01-01 로 보인다. 따로 고친다.
