# 미확정 사항

**아직 정하지 않은 것을 적는다.** 여기 있는 것은 **건드리지 않는다** — 급해서 각자 정해버리면
나중에 서로 다른 전제 위에 쌓인 코드를 뜯어야 한다.

정해지면 이 줄을 지우고 계약(`api-spec.md`)이나 결정(`docs/adr/`)으로 옮긴다.

```
상태     ⬜ 안 정함   🔶 자료 기다림   ✅ 정해져서 옮김
```

---

## 🔶 U-1 · 만3~5세 양식을 본 적이 없다

**지금 §11 · ADR-024 · S-J1 이 전부 만1~2세 영아 자료 위에 서 있다.**

```
가진 것   PR #124 — 파일 11건 · 원 2곳 · 양식 3종
          일일·관찰기록은 B원 만1~2세, 주간만 A원 만2·3세
우리 대상  만 3~5세 유아반 담임교사 (PRD)
```

**관찰일지와 보육일지는 따로 본다.** 둘이 영아 ↔ 유아에서 달라지는 **이유가 다르고,
우리 코드가 그 차이를 받는 방식도 달라서 급한 정도가 다르다.**

| | 왜 달라지나 | 우리 코드가 어떻게 받나 | 급한가 |
|---|---|---|---|
| 관찰일지 (U-1a) | 국가가 영역 목록을 정한다 | **코드에 상수로 박혀 있다** | 🔴 양식이 다르면 코드를 고쳐야 한다 |
| 보육일지 (U-1b) | 그 나이의 하루가 다르다 | **교사가 직접 친다** | 🟡 양식이 달라도 적으면 들어간다 |

### 🔴 U-1a · 관찰일지 — 영역 목록이 다르다

**교육과정이 다르다.** 원이 바꾸고 싶어도 못 바꾼다 — 평가인증 서류라 교육과정을 따른다.

```
0~2세  표준보육과정  6영역   기본생활 · 신체운동 · 의사소통 · 사회관계 · 예술경험 · 자연탐구
3~5세  누리과정     5영역   신체운동·건강 · 의사소통 · 사회관계 · 예술경험 · 자연탐구
```

영아에만 **「기본생활」**이 독립된 영역으로 있다. 먹기·자기·배변·청결이 그 나이엔 보육의
큰 축이라서다. 유아로 가면 「신체운동·건강」 안으로 들어간다. **그래서 행 개수부터 다르다.**

**우리 코드는 이미 유아 기준이다** — `backend/app/features/observations/models.py:24` 가
누리과정 5영역으로 못 박혀 있다. 영역 이름 자체는 안 물어도 된다.

**그런데 이미 걸린 자리가 하나 있다.**

```
api-spec.md:1111
  실물 양식에는 「기본생활습관」 행이 하나 더 있다.
  §10 domain 에 없어서 비워 둔다 — 다음 개정.
```

영아 양식에 있던 칸을 우리 `domain` 이 못 받아서 **빈칸으로 두고 넘어갔다.** 영아만의
칸이면 유아에서는 문제가 안 되고, **유아 양식에도 있으면 지금 관찰일지에 구멍이 하나 있는
것**이다. 지금은 모른다.

**양식을 받으면 이것부터 본다**

```
영역이 몇 개인가 · 이름이 무엇인가
「기본생활습관」 행이 있나          ← 있으면 domain 에 추가해야 한다 (코드 수정)
한 장에 아이 몇 명 · 기간이 얼마인가  (U-5 와 같이 본다)
```

### 🟡 U-1b · 보육일지 — 하루 구성이 다르다

보육일지는 **반 하나의 하루**를 시간 순서로 적는다. 영역 칸이 없다. 그런데도 다르다 —
**그 나이의 하루가 다르기** 때문이다.

```
영아(0~2세) 하루   수유 · 이유식 · 기저귀갈기 · 배변 · 낮잠(길고 여러 번) · 개별 돌봄
유아(3~5세) 하루   자유놀이(흥미영역) · 대소집단활동 · 바깥놀이 · 급식 · 양치 · 특별활동
```

`[실측 #124]` B원 일일 보육일지의 자유놀이 행이 영역 7개로 쪼개진다 —
**언어 · 신체 · 감각탐색 · 미술 · 역할 · 쌓기 · 음률.** 「감각탐색」은 영아 흥미영역
이름이다(유아는 보통 「과학」·「탐구」). 이 한 단어가 그 양식이 영아용이라는 표시다.

**우리는 이미 막아 놨다.** 일과 이름을 드롭다운으로 안 만들고 **교사가 치게** 했다(S-J1).
영아든 유아든 원마다 다르든 교사가 적는 대로 들어간다. 그래서 U-1b 는 코드를 안 막는다.

**반대 증거도 있다** `[실측 #124]` — A원 주간 양식은 **만2세반과 만3세반이 같은 틀**이다.
만2세는 영아, 만3세는 유아인데 한 원에서 그 선을 넘어 같은 양식을 썼다. 표 구조는 연령보다
**원마다** 다를 수 있다는 뜻이다. 다만 표본이 원 한 곳 · 주간 하나라 단정 못 한다.

**양식을 받으면 이것부터 본다**

```
일과 행이 몇 개인가
자유놀이를 흥미영역으로 쪼개나        (U-6)
해석과 지원이 한 칸인가 두 칸인가     (ADR-024 가 여기서 나왔다)
```

**누가 푸나** — 수민 · 덕철 수집(만3~5세 · 원 5~8곳) → `결정.md` 에 합친 정리 →
§11 · ADR-024 재검토. **U-1a(관찰일지)를 먼저 모은다** — 그쪽만 코드를 막는다.

## ⬜ U-2 · 주간 보육일지를 만들 것인가

```
api-spec §11   weeklyLog 가 문서 4종 중 하나로 들어 있다. 서버도 절반 돈다
PRD            「P1 일지 계열 — 관찰일지 · 보육일지」. 일일인지 주간인지 안 적혀 있다
CLAUDE.md      같다
결정.md         없다
```

**정한 적이 없는데 계약에만 있다.**

```
[실측 #124]  A원은 주간으로만, B원은 일일로만 쓴다. 원마다 하나를 고르는 것으로 보인다
            원이 2곳뿐이라 비율을 모른다
```

**누가 푸나** — 수집이 끝나면 「주간 쓰는 곳 : 일일 쓰는 곳」이 나온다. 파일럿 교사님께도 묻는다.
정하면 PRD 의 「보육일지」를 「일일 보육일지 · 주간 보육일지」로 고치고 ADR 을 남긴다.

## 🔶 U-3 · 주간 보육일지 · 영유아 평가를 한글 파일로 뽑을 때 칸을 어떻게 나누나

우리 화면은 **사실 · 해석 · 지원** 세 칸으로 나뉜다. 그런데 교사가 원에 내는 실제 양식에는
그 세 칸이 그대로 있지 않다 — 실물을 보니 **해석과 지원이 한 칸에 같이** 들어가 있었다.

그래서 ADR-024 로 정했다. **화면에서는 세 칸으로 나누고, 한글 파일로 뽑을 때만 합친다.**

```
                     화면      한글 파일
관찰일지               3칸      해석+지원을 한 칸으로    ← ADR-024 가 정함
일일 보육일지           3칸      해석+지원을 한 칸으로    ← ADR-024 가 정함
주간 보육일지           3칸      ?                    ← 안 정함
영유아 평가             3칸      ?                    ← 안 정함
```

ADR-024 를 쓸 때 본 실물이 관찰일지와 일일 보육일지뿐이었다. §11 도 「`weeklyLog` ·
`assessment` 는 이번 범위 밖」이라고 적고 넘어갔다.

[실측 #124] 주간은 A원 양식의 칸 구조를 수린이 적어둬서 거기서 시작하면 된다.
**영유아 평가는 실물을 한 장도 못 봤다.**

**지금 정하지 않는 이유** — 둘 다 아직 안 만드는 문서다. 주간 보육일지는 만들지 말지부터
안 정했고(U-2), 영유아 평가는 11~12주차다. 안 만드는 문서의 칸 배치를 지금 정하면
나중에 실물 보고 다시 뒤집는다.

**누가 푸나** — U-1 자료 + 수린(§11 계약 담당)

## ⬜ U-4 · 3단 LLM Judge 를 언제 부르나

```
api-spec      POST /api/documents/{id}/verify    3단 LLM Judge
              계약은 다 적혀 있다. 구현만 0
```

**§11 이 이미 정한 것 — 여기서 다시 정하지 않는다**

```
결과 모양     { "issues": [] }.  비면 통과, 아니면 각 항목이 이유와 수정 지시
무엇을 잡나   미관찰 행동·발언·횟수·성취 / 성향 단정·발달 진단 / 근거 없는 해석
              지원이 없거나 형식적이거나 무관 / source_id 가 그 문장을 안 받침
반려 뒤       저장하지 않는다. 교사가 고치고 다시 부른다
확정 조건인가 아니다 — §11 이 「확정에 3단을 요구하지 않는다」고 적었다
```

**안 정한 것 — 이것뿐이다**

```
언제 부르나        교사가 [검증] 을 누르나, 저장할 때 자동인가, 확정 누를 때 한 번인가
반려가 화면에 어떻게 보이나   issues 를 어디에 띄우나 — 문장 옆인가 위쪽 띠인가
```

**누가 푸나** — 수민 · 수린

> 확정 조건이 아닌데 교사가 굳이 누를 이유를 화면이 만들어 줘야 한다. 부르는 때가 안 정해지면
> 만들어도 아무도 안 쓴다 — 막힌 건 판정 내용이 아니라 이 자리다.

## ⬜ U-5 · 관찰일지의 「아이 × 기간」 묶기 규칙

ADR-024 가 **「관찰일지 한 장에는 아이 한 명의 한 기간치 5영역이 들어간다」**고 정했는데,
어디서 끊어 한 장으로 묶을지가 없다.

```
기간을 누가 정하나      교사가 고르나 · 한 달 고정인가
그 기간에 관찰이 20건이면  다 넣나 · 영역당 몇 개까지
같은 영역 3건이면        어떻게 잇나 (날짜 순? 줄바꿈? 고르게 하나)
기록이 없는 영역         [판단] 빈 칸으로 두고 화면이 알린다 — §11 에 있음
```

[실측 #124 · B원] **영역당 관찰 1건, 날짜 1개**였다. 원 1곳이라 일반적인지 모른다.

**누가 푸나** — 수민(서버) · 덕철(화면). U-1 자료가 오면 같이.

## ⬜ U-9 · 관찰 기록을 칸으로 쪼갤 것인가

지금 관찰 기록은 **사실 한 칸**이다(아이 · 날짜 · 영역 · 상황 + `fact` 자유 서술).
교사가 「블록 쌓고 놀았음」 한 줄을 적으면 **AI 가 거기서 뽑아낼 것이 없다.**
관찰일지 품질의 천장이 이 칸에서 정해진다.

`[참고]` 현장 교사 챗봇(소리네공방)은 **질문 12개를 하나씩 던져** 이걸 채운다 —
이름 · 날짜 · 활동 · 장소 · 함께 있던 사람 · 놀잇감 · 행동 흐름 · 표정과 말 ·
주변 반응 · 교사 개입 · 반복 여부 · 주목한 점.

**2026-10-15 에는 안내만 넣었다** — 「상황 → 행동 → 반응 → 교사 지원」 순서를
입력칸에 보여준다(FR-404). 칸은 안 늘렸다.

**안 정한 것**

```
칸을 쪼갤 것인가        쪼개면 AI 가 뽑아낼 필요 없이 그대로 쓴다
                       평가제 추적도 쉬워진다 (「교사 지원」이 따로 있으면)
몇 개로                 12개는 너무 많다 — 관찰 한 건마다 12번 답하면 안 쓴다
                       챗봇은 하나씩 물을 수 있지만 우리 화면은 한 장이다
```

**왜 지금 못 정하나 — `U-1a` 가 먼저다**

실제 유아 관찰일지 양식에 칸이 몇 개인지 모른다. 양식이 「관찰내용 / 평가」 두 칸인데
우리가 넷으로 쪼개면, 종이로 뽑을 때 다시 합쳐야 한다. **또 틀린 전제 위에 쌓는 것이다.**

**같이 바뀌는 것** — 칸을 쪼개면 이 셋이 딸려 온다.

```
사실 층의 뜻      「교사 원문 그대로」가 원칙인데, 쪼개면 그 「원문」이 무엇인지 다시 정해야 한다
stale 판정        지금은 fact 문자열 하나를 비교한다 (§11)
마이그레이션       기존 기록을 어떻게 나눠 담을지
```

**누가 푸나** — `U-1a` 양식이 모인 뒤 수민 · 승석. 양식의 칸 수에 맞춘다.

## ⬜ U-10 · 주간 계획을 어떤 문서로 내보내나 (원 ID OD-W02)

**주간계획안을 P0 에 넣고 월간을 거쳐서만 만든다는 것은 정했다**(ADR-030 PM-04). **무엇으로 내보내나는 아직이다.**

```
후보   ① 별도 주간계획안   ② 주간 보육일지의 계획 칸   ③ 일일 보육일지의 계획 칸
권장   ① 하나부터 — 하나의 의미 구조(WeeklyPlan)와 출력 위치별 Adapter 를 나누고 첫 Adapter 만 연다
근거   주간 샘플 125개가 모두 별도 주간계획안이다(PR #173 조사).  ②③ 은 일지 쪽 결정(U-2)과 엮인다
```

**누가 푸나** — 주간 계약(W1) 초안과 함께 하민 · PM. screen-spec S6a 질문 2 · api-spec `plan-config weekly_location` 이 이 답을 기다린다.

## ⬜ U-11 · 주간 토요일 설정을 어디에 어떻게 두나

**정책은 정했다**(ADR-030 WQ-01) — 기본 월~금 5일, 원 설정으로 토요일을 켠다, 2주 단위는 지원하지 않는다.
**데이터 계약이 아직이다.**

```
정할 것   설정을 어디에 저장하나(원 설정 · plan-config · 주간 Template)
          Core WeekPeriod(월~금 고정)와 어떻게 이어지나 — 주차 번호(YYYY-MM-Wn)는 바꾸지 않는다
          월 경계 주의 판정(「그 달 평일 3일 이상」)에 토요일을 세나
          설정을 바꾸면 이미 만든 주간계획안은 어떻게 되나
```

**누가 푸나** — 주간 계약(W1)에서 하민. 연간 · 월간 주차 계약과 호환되어야 한다.

## ⬜ U-12 · 기존 연간계획안 이어받기 — 받을 형식 (원 ID OD-N09)

**지원 형식이 정해질 때까지 비활성이다**(ADR-030 PM-11). 승인 목록에 없는 파일을 추측으로 읽지 않는다.

```
정할 것   받을 형식 · 버전 목록, 파일 크기 · 인코딩 제한, 월 · 칸 매핑, 비었거나 미작성인 달의 판정,
          사용자 확인 단계, 부분 생성 기준, 실패 · 경고 응답
```

**누가 푸나** — 이어받기 기능을 시작할 때. screen-spec S6b 가 비활성 표시를 한다.

## ⬜ U-13 · LLM 재시도 · 최종 실패 정책의 수치 (원 ID OD-N04 남은 부분)

모델(`gpt-6-luna`, ADR-023)과 호출 경로 · 오류 분류(ADR-036)는 정했다. **재시도 횟수 · 최종 실패 처리의 수치가 남았다.**
지금은 호출 타임아웃 30초 · 자동 재시도 없음 · 수리 1회(ADR-033)다. 월간 동기 실행은 조건부 채택이다(ADR-036 §2).

**누가 푸나** — 운영 호출 기록을 본 뒤 하민.

---

## ⬜ U-14 · Evidence 수집 도구의 PDF 라이브러리 의존성 (원 ID OD-N16)

근거 자료(Evidence Store)를 다시 만드는 도구가 PDF 라이브러리를 쓴다. 지금은 프로젝트 의존성에 넣지 않고 빌드할 때만 따로 설치한다.
**CI 에서 다시 만들지, 넣는다면 일반 의존성인지 선택 의존성인지, 라이선스(AGPL / 상용) 검토**가 남았다.

**누가 푸나** — Evidence Store 재빌드를 자동화할 때.

---

## ⬜ U-15 · 근거의 연령 강도를 몇 단계로 보여 주나 (원 ID OD-N17)

월간 근거 묶음(Context Packet)의 연령 강도는 지금 4단계(`STRONG` · `MODERATE` · `WEAK` · `VERY_WEAK`)다. 3단계로 줄일지가 미결이다 —
줄이면 「근거가 적다」와 「근거가 없다」를 화면에서 같게 안내하게 된다.

**누가 푸나** — 화면이 연령 강도를 보여 주기로 할 때.

---

## ⬜ U-16 · 연간 동시 수정 — 다중 교사 이후 (원 ID OD-N06 일부)

**P0 는 서버 행 잠금으로 막는다**(ADR-030 PM-05, ADR-035 §3). 확정이 되돌아가는 경로는 막지만, 두 교사가 서로 다른 때 읽고 쓰는 덮어쓰기는 남는다.
**다중 교사(#139 초대 코드)가 실제로 쓰이면 연간에도 `expected_revision` 을 둘지 다시 본다.** 자동 저장 · 확정 이후 새 버전도 미결이다.

**누가 푸나** — 파일럿에서 한 반을 여러 교사가 쓰기 시작할 때 하민 · 승석.

## ⬜ U-17 · 월간 콘텐츠 후속 결정 3건 (원 ID OD-V01 ~ OD-V03)

OD-V01   주 경험(Week Experience) 자료의 정식 키 이름
OD-V02   근거가 아주 적은 달(6 · 7 · 8 · 1월)을 비워 둘지, 자료를 더 모을지
OD-V03   활동에 표시 이름을 따로 둘 때 원문을 어디에 보존하나

**누가 푸나** — 주 경험 참고자료를 발행하거나 활동 참고자료를 넓힐 때 하민.

## ⬜ U-18 · Core 오류를 어디서 감싸나 (원 ID pr/12 후속 3건)

```
1  YearlyRuleError · MonthlyRuleError 를 code 가 있는 Application 오류로 감쌀지
2  InvalidStateTransitionError 같은 Domain 오류도 Application 오류 경계 안으로 넣을지
3  Port 를 가져오는 공식 경로(예: ssuksak.planning.ports)를 따로 둘지
```

지금은 감싸지 않은 Rule 오류가 Backend 까지 올라오면 일반 텍스트 500 이 된다(Core Error Audit, 2026-10-19). 정상 경로에서는 나오지 않는다.

**누가 푸나** — Core 오류 목록 정리(#155 3순위)와 함께 하민.

## ⬜ U-19 · 예상하지 못한 500 의 응답 형식 (Core Error Audit I-3)

잡지 않은 예외는 지금 `text/plain` 「Internal Server Error」로 나간다 — 공통 오류 형식(`{"error": {...}}`)이 아니다.

```
후보   ① 공통 형식으로 감싼다 — 어떤 code 를 쓸지 정해야 한다
       ② 일반 텍스트 그대로 두고 api-spec 에 예외로 적는다
```

FE 는 지금도 깨지지 않는다(기본 문구를 띄운다). **새 공개 코드를 만드는 결정이라 PM · 팀 몫이다.**

## ⬜ U-20 · 연간 「그 달 · 연령에 쓸 주제 후보가 없다」의 공개 코드 (Core Error Audit I-4)

승인된 주제 참고자료에 그 달 · 반 연령을 지원하는 후보가 없으면 지금 422 `VALIDATION_FAILED` · `fields: []` 에 Core 영문 문장이 나간다.

```
후보   ① 422 VALIDATION_FAILED ["class_id"] + 고정 문구 — 반 연령을 바꾸면 풀린다
       ② 503 DEPENDENCY_UNAVAILABLE — 참고자료가 모자란 운영 문제로 본다
```

**누가 푸나** — 연간 오류 매핑 정정 PR(#171 머지 뒤) 전에 PM · 팀.

## 정해진 것 (옮김)
