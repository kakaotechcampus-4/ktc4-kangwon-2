## 결정을 글로 남긴다

- **되돌리기 어려운 결정은 `docs/adr/` 에 파일 하나.** 스택 · 폴더 구조 · 데이터 모델 · 외부 의존 추가 · 기능 스펙아웃
- 이유: 코드에는 결과만 남고 **대안과 근거는 사라진다.** 3주 뒤에 "이거 왜 이렇게 했지"를 묻는 사람은 우리 자신이다
- **문서끼리 충돌하면 순서를 정해 뒀다** — `ADR > api-spec > 요구사항명세서 > screen-spec`, 같은 단계면 늦은 결정이 이긴다 (ADR-031)
- **저장소 밖 문서를 근거로 인용하지 않는다** — 개인 문서 · 브랜치에만 있는 문서 (ADR-031)
- 뒤집힌 결정을 지우지 않고 **뒤집혔다고 적는다** — ADR-005 → ADR-014 → ADR-032, ADR-003 의 결정론 전제 무효

## 일하는 규칙

- 브랜치 — 기능은 `feature/*`, 멘토 피드백 반영은 `refactor/*`, 둘 다 `develop` PR.
  `develop` → `main` PR 이 **멘토 리뷰 요청**이다. `main` 머지는 PM 만 — [docs/branch-strategy.md](../branch-strategy.md)
- 주차마다 사람별 To-do 이슈 — #150~#155(10~11주차) · #244~#250(12주차)
- 담당을 나눌 때 **그 화면의 디자인·UI 전권까지 같이 준다** — 12주차에 평가제 점검(수린) · 문서 보관함(덕철)
- 팀 공통 규칙은 [CLAUDE.md](../../CLAUDE.md) 한 장. `p0-planning/` 안에는 더 좁은 규칙이 따로 있고 거기서는 그게 우선한다
- 「짐작하지 말고 묻는다」 — 요청이 두 가지로 읽히면 둘 다 적어 되묻는다 ([CLAUDE.md](../../CLAUDE.md) §일하는 방식 ①)

## 아직 아닌 것

- **코드리뷰가 아직 절반이 안 된다.** 최근 머지된 PR 30건(11/1~11/4) 중 사람이 리뷰나 코멘트를 단 것은
  **13건**(10/27 집계 9건), 리뷰 **9** · 코멘트 **6**이다 — 봇(Codex) 것은 뺐다
  (`gh pr list --state merged --limit 30 --json reviews,comments`). 평가 관점이 「코드리뷰가 실제로 활발한가」라
  여기서 깎인다. **남은 기간에 서로 리뷰를 달면 바로 메워지는 자리다**
- **회의록이 저장소에 없다.** ADR 과 이슈로 대신하고 있다
